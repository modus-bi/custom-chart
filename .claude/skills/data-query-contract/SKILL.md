# Запрос данных и приведение ответа

## Суть

Цепочка загрузки в шаблоне собрана, но пуста в нескольких местах, и **первый разрыв срабатывает
раньше `loadDatas`**: `ConfigEditor.addField` возвращает конфиг без изменений, поэтому брошенная
на полку пилюля в `config.axes[].fields` не попадает. Без неё `getDatasetId` возвращает
`undefined`, эффект `CustomChart` выходит до вызова, и запрос не уходит вовсе — а не «уходит
пустым».

Порядок разрывов, по очереди срабатывания:

| #   | Что                                                                 | Следствие                                    |
| --- | ------------------------------------------------------------------- | -------------------------------------------- |
| 1   | `ConfigEditor.addField` / `addAllFields` / `updateField` — заглушки | пилюля не попадает в конфиг, `datasetId` нет |
| 2   | `CustomAxes.sortAxes` возвращает `[]`                               | панель полок пуста — ронять пилюлю некуда    |
| 3   | `DataAdaptor.getQueryObjects` возвращает `[]`                       | запрос без `select`                          |
| 4   | `aggregateBypass` и `remapData` — пустые тела                       | `plotData` всегда пуст                       |

Скилл — про пункты 3 и 4. Но начинать доработку с них бессмысленно: сперва пункт 1, иначе
проверить запрос будет не на чем. Возвращаемое `ConfigEditor.addField` значение **и есть** новый
`configDraft` — редьюсер ядра кладёт его в состояние как есть, поэтому «заглушка возвращает
конфиг без изменений» на деле означает «перетаскивание пилюли не работает».

Скилл описывает форму запроса и форму ответа. Что делать с готовым `plotData` дальше —
`chart-shell` (разметка) и правила отрисовки.

## Источники истины

Форма запроса и форма ответа контрактом не описаны: `chartPlugin.d.ts` объявляет `data`, `spec`
и `config` как `any`. Проверять их нужно по двум местам, оба локальные:

- **Бандл ядра** в `prebuild/`. Правило именования ключей ответа задано функцией `splitTraces`
  и читается грепом (см. раздел про форму ответа). Так же проверяется всё остальное, в чём
  возникает сомнение, — грепом по `prebuild/app.*.js`, а не по памяти.
- **Реальный ответ бэкенда** на своём отчёте. Он старше любых рассуждений о том, каким ответ
  «должен» быть.

Всё, что описано ниже, — свод правил, добытых из этих двух источников. Если твоя сборка ядра
даёт другое, права она, а не скилл: перепроверь и поправь скилл.

## Модель: один трейс на пилюлю «Значений»

Главное, что нужно понять до первой строки кода: **`getQueryObjects` возвращает не один объект
запроса, а массив** — по объекту на каждую пилюлю полки «Значения».

```
Полки:  Значения [Выручка, Прибыль]   Категории [Регион]
                          ↓
queryObjects = [
  { select: [Выручка, Регион], group: [Регион], order, where, having, options, limit },
  { select: [Прибыль, Регион], group: [Регион], order, where, having, options, limit },
]
```

Секции `group`, `order`, `where`, `having` у всех трейсов общие; различается только первый
элемент `select` — само значение. «Общие» здесь не наблюдение, а **требование к реализации**:
сливая трейсы в один запрос, `mergeTraces` читает `group`, `order`, `distinct` и `limit`
**только из `queryObjects[0]`**. Что положено в остальные трейсы, до бэкенда не доедет.

Отсюда порядок обхода: **полки `series` и `categories`
обрабатываются раньше `values`**, иначе к моменту сборки трейса группирующие поля ещё не
накоплены. В ядре это сделано сортировкой полок перед циклом (`series` → `-2`,
`categories` → `-1`, остальные → `0`).

Пилюля с `hideResult` трейса не порождает. Пустой массив полок — ядро возвращает `false`,
а не `[]`.

## Секции объекта запроса

| Секция      | Что несёт                                                                              |
| ----------- | -------------------------------------------------------------------------------------- |
| `select`    | значение трейса первым элементом, за ним — группирующие поля                           |
| `group`     | группирующие поля, по одному на имя (повторы по `name` исключаются)                    |
| `order`     | сортировка; собирается отдельно и раскладывается по `orderIndex`                       |
| `where`     | поля полки «Фильтры» с `filterSqlType === 'where'` или без него                        |
| `having`    | поля полки «Фильтры», у которых `type === 'calculated'` и `filterSqlType === 'having'` |
| `options`   | `{ seriesAutoFill }` из `config.series.autoFill`                                       |
| `variables` | переменные отчёта, если `config.variables` не пуст                                     |
| `limit`     | `config.rowsLimit`                                                                     |

**Значения фильтров в `queryObjects` не идут.** Описание поля фильтра попадает в `where`,
а выбранные пользователем значения ядро передаёт третьим аргументом `loadDatas`
(`config.filters`) — это разные вещи, и путать их не нужно.

**Секцию `where` ядро всё равно собирает заново.** В `mergeTraces` она перезаписывается
целиком: `where` — из `config.filters`, `having` — оттуда же. Плагинский `where` до бэкенда
не доезжает; `having` в объекте запроса нужен лишь как признак «этот фильтр — HAVING»
(ядро ищет по `name`) и как источник выражения `calc`. Заполнять обе секции нужно — по ним
ядро принимает решения, — но ждать, что именно они уйдут в запрос, не стоит.

## Ловушка `cacheId`: ответ уходит в чужую ячейку

Самая дорогая ошибка этого участка, и она не в форме запроса.

Коннектор компонента считает `props.cacheId` **по своим** `queryObjects` — вызовом штатного
`CommonDataAdaptor.getQueryObjects(config)`, а не плагинского. `loadDatas` же, получив запрос
плагина, считает ключ заново из своих аргументов. Разошлись хоть одним полем — ответ лёг в
ячейку с другим ключом, а `props.data` остаётся `undefined` навсегда: запрос ушёл, данные
пришли, компонент их не видит.

**Решение проекта: передавать `props.cacheId` шестым аргументом `loadDatas`.**

```ts
loadDatas(datasetId, null, config.filters, queryObjects, { editor, componentId }, cacheId);
```

Шестой аргумент перекрывает расчёт ядра (`cacheId || getCacheId(...)`), поэтому ответ ложится
ровно в ту ячейку, из которой компонент читает, — независимо от того, насколько плагинский
запрос разошёлся со штатным.

Чем платим: ячейка перестаёт протухать от изменений, которые видит только плагин. Если запрос
зависит от собственной настройки панели (а `props.cacheId` про неё не знает), выборка останется
прежней — за перезапросом идти к инжекту `reloadDatas` с той же сигнатурой.

**Второй побочный эффект важнее первого: ответ приходит не в проп `data`, а в
`props.datas[cacheId]`.** Снято на живом портале. Поэтому компонент читает **оба** места:

```ts
const response = data || datas?.[cacheId];
```

Прежний путь через `data` остаётся рабочим — по нему ответ приходит, когда ядро `cacheId` не
передало вовсе. Оставить только один из двух — значит получить пустой компонент на половине
сценариев, причём на той половине, которую не видно в тестах.

Чего не делать: добиваться побайтового совпадения своих `queryObjects` со штатными. Совпадение
придётся заново проверять после каждого обновления ядра, а расходится оно молча.

Второй рабочий путь — считать ключ самому (`pluginImports.helpers.getCacheId`). Он гибче в части
протухания, но требует самому отслеживать, когда ключ меняется; в шаблоне он не выбран.

## Автообновление: таймер заводит плагин, запрос идёт через `reloadDatas`

Речь про автообновление **данных**. Одноимённый тумблер в шапке панели настроек
(`autoApplyToggleContent`) — про другое: он управляет применением настроек, «сразу / по кнопке».

«Автообновление» и «Интервал обновления (секунды)» — пункты готовой секции ядра «Настройки
данных» (`DataOptionsContent`). Секция пишет `config.refresh` и `config.refreshTime` своими
колбэками, мимо редьюсера плагина, — но **таймер перезапроса ядро за плагин не заводит**:
штатные компоненты крутят `setInterval` у себя внутри, и плагин обязан сделать то же. Пока он
этого не сделал, тумблер в панели есть, а данные не обновляются — и выглядит это как отказ
плагина, а не как незаведённая функция.

Перезапрос идёт инжектом **`reloadDatas`**, а не `loadDatas`, теми же шестью аргументами:

```ts
setInterval(() => {
  reloadDatas(datasetId, null, config.filters, queryObjects, { editor, componentId }, cacheId);
}, refreshTime * 1000);
```

`loadDatas` для этого не годится: при уже лежащем в `datas` ответе он нового запроса не делает,
а возвращает содержимое кэша. `reloadDatas` сбрасывает запись и запрашивает заново.

Три места, где такой таймер ломается:

- **инжект и конфиг в зависимостях эффекта.** Ядро вправе отдавать инжект новым замыканием на
  каждый рендер, а конфиг меняет ссылку при каждой правке настроек: интервал пересоздаётся и не
  дотикивает до срабатывания ни разу. Брать оба внутри таймера из `ref`, а в зависимостях
  держать примитивы — `refresh`, `refreshTime`, `datasetId`, `cacheId`, `componentId`,
  `editorActive`;
- **отсутствие снятия.** Без `clearInterval` в функции очистки эффекта переоткрытый отчёт
  оставляет за собой тикающие таймеры;
- **чтение полей напрямую.** В отчёте, сохранённом до появления настройки, `refresh` и
  `refreshTime` отсутствуют — читать через `readConfigField` (скилл `new-setting`).

Отдельное решение — гонять ли таймер в редакторе (`editor`): пока идёт настройка компонента,
дёргать бэкенд обычно незачем. Это продуктовый выбор, и он согласуется с пользователем, а не
додумывается.

## Поля элемента `select`

| Поле         | Что кладут                                                                            |
| ------------ | ------------------------------------------------------------------------------------- |
| `name`       | имя поля в датасете; при наличии `field.parameters` — массив `[name, ...parameters]`  |
| `calc`       | выражение вычисляемого поля, пропущенное через `hsQuote` (замена `!hs_quote!` на `'`) |
| `aggr`       | агрегация (`field.agg`) или пустая строка                                             |
| `alias`      | адрес колонки в ответе — см. следующий раздел                                         |
| `id`         | `field.id`, по нему строка ответа связывается с пилюлей конфига                       |
| `fieldAlias` | подпись: `title` (с учётом языка) или `alias`, или `name`                             |
| `lvl`        | уровень вложенного запроса набора данных, `field.lvl                                  |     | 0`  |
| `valueType`  | тип значения: `value`, `threshold`, `color`, `info`, `min`, `max`…                    |
| `distinct`   | появляется вместе с заменой `aggr: 'countd'` → `aggr: 'count'`                        |

Агрегация `countd` до бэкенда не доезжает: ядро заменяет её на `count` + `distinct: 1`.

## Алиасы: откуда квадратные скобки

Алиас — это имя колонки, под которым значение вернётся в ответе. Строится из **типа полки**:

| Полка       | Алиас          |
| ----------- | -------------- |
| «Значения»  | `[values]`     |
| «Категории» | `[categories]` |
| «Серии»     | `[series]`     |
| «Фильтры»   | `[filters]`    |
| «Детали»    | `[values]`     |

**Алиаса `[details]` не существует.** Полка «Детали» обрабатывается ядром в одной ветке со «Значениями» (`case "values": case "xvalues": case "yvalues": case "rows": case "details": case "columns": case "keys":`) и получает тот же жёстко прописанный `alias: '[values]'`. Проверяется одной командой:

```bash
grep -c "\[details\]" prebuild/app.*.js   # 0
```

**Индекса в алиасе значения тоже нет.** `getQueryObjects` ставит ровно `[values]`; индекс `[values][0]`, `[values][1]` приписывает уже `mergeTraces` при слиянии трейсов в один запрос.

К алиасу добавляется **суффикс индекса**, когда на полке несколько пилюль:
`getAliasSuffix` даёт `[<индекс пилюли>]` для «Категорий» с `selectedFieldIndex === -2`
и для «Серий» при `chartType === 'table'`. Так рождаются ключи `[categories][0]`,
`[categories][1]`. Сортировка по другому полю добавляет ещё и `_sortBy`:
`[categories][0]_sortBy`.

## Форма ответа: правило `splitTraces`

Бэкенд отдаёт **одну таблицу**, где значения разных пилюль лежат в колонках `[values][0]`,
`[values][1]`, …. Раскладывает её по трейсам функция `splitTraces` ядра
(`prebuild/app.*.js`) — и она же задаёт правило, по которому ключи переименовываются:

```bash
grep -o "splitTraces=.\{0,700\}" prebuild/app.*.js
```

Правило ядра, дословно:

1. Ключи `[values][n]` становятся **отдельными трейсами**; в строке трейса значение лежит
   под общим ключом **`values`** — без индекса и без скобок.
2. Скобки снимаются **только** у точного совпадения с одним из пяти:
   `[categories]`, `[series]`, `[identity]`, `[linkage]`, `[node]` → `categories`, `series`,
   `identity`, `linkage`, `node`.
3. **Все остальные ключи остаются со скобками как есть**: `[categories][0]`,
   `[categories][1]_sortBy`. Список из пункта 2 — сравнение на равенство, а не на префикс,
   поэтому `[categories][0]` в него не попадает.
4. Строки измерений копируются в **каждый** трейс — у трейсов общая часть и своё `values`.
5. Если колонок `[values]` в ответе нет вовсе, работает другая ветка: скобки снимаются
   со **всех** ключей, а каждая строка становится отдельным элементом.
6. `groupByOptimization` в конфиге выбрасывает `[categories]` из общей части строки.

Отсюда практическое:

```ts
row.values; // значение трейса — всегда так
row.categories; // одна пилюля на полке «Категории»
row['[categories][0]']; // несколько пилюль — скобки остаются
```

**`splitTraces` ядро зовёт само, до записи в стор** — плагину `props.data.data` приходит уже
массивом трейсов (`data.data[i]` — строки i-го трейса, значение под ключом `values`). Вызов
стоит внутри обработчика ответа, рядом с `receiveData`; экспорт находится грепом по
`splitTraces=`. Самому её звать не нужно, а при попытке — учти, что на ключе ровно `[values]`
без индекса она падает с `TypeError` (регулярка не находит номер).

Реальную форму всё равно печатать:

```ts
console.log(JSON.stringify(data?.data, null, 2)); // в CustomChart, до сборки адаптора
```

и сверить с моделью выше. Это дешевле любого рассуждения о том, какой ответ «должен» быть.

## Три уровня данных

Ответ ядра компоненту — не только `{ fetching, data }`: там же `cached`, `cropped`
(выборка обрезана лимитом), `error`, `errorMsg`, `msg`. Именно `error`/`errorMsg` закрывают
поле требования «ошибка запроса»: компонент, который строит адаптор на любом `!fetching`,
на ответе с ошибкой построит его по пустоте и покажет пустой холст вместо сообщения.

| Уровень      | Что это                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `source`     | ответ как пришёл, разложенный по `datasetId`, обрезанный по лимитам строк и серий                                                    |
| `aggregated` | массив трейсов; строка = строка ответа + метаданные своей пилюли (`name`, `id`, `fieldName`, `fieldAlias`, `fieldTitle`, `traceKey`) |
| `plotData`   | строки для отрисовки: `plotData[i]` собран из `aggregated[*][i]`                                                                     |

`aggregated[0].length` — число строк: все трейсы считаются одинаковой длины, `remapData` идёт
по индексам первого.

Ключ значения меняется между уровнями, и это самая частая путаница: в `aggregated` значение
лежит под `values`, а в `plotData` — под ключом, который выбирает **твой** `remapData`.

**Ключ значения в `plotData` — `elem.id`, идентификатор пилюли.** Так делает штатный `remapData`
ядра, и так же делаем мы. Причина в единственном сценарии, который ломает альтернативу: две
одинаковые пилюли на полке «Значения» с одной агрегацией дают одинаковое
`"<имя поля> (<агрегация>)"`, и второе значение затирает первое — молча, без ошибки.

Плата — читаемость: в фикстурах и в спеке отрисовки вместо «Выручка (sum)» стоит
`"Выручка_a3f9"`. Для отладки рядом в строке лежат `name`, `fieldName` и `fieldTitle` — по ним
видно, что это за трейс, а спека всё равно строится из конфига, где `id` пилюли известен.

## Минимальная реализация

Скелет для шаблона: одна полка значений, одна-две группирующие, фильтры в `where`. За его
рамками остаётся то, что нужно не всякому плагину и добавляется по мере надобности:

| Не покрыто скелетом         | Что добавляет                                                                             |
| --------------------------- | ----------------------------------------------------------------------------------------- |
| Вычисляемые поля            | `calc` в элементе `select` и в `group`, пропущенный через замену `!hs_quote!` на апостроф |
| Сортировка по другому полю  | ещё один элемент `select` с суффиксом `_sortBy` и агрегацией `max`                        |
| Подпись и цвет по полю      | элементы с суффиксами `_labelBy` и `_colorBy`, агрегация `max`                            |
| Секция `order`              | сборка по `field.order` и раскладка по `field.orderIndex`                                 |
| Подытоги (`config.subMode`) | сброс агрегаций у всех полей `select`                                                     |
| Экспортные режимы           | подмена подписей на заголовки колонок, отдельная ветка для сводных таблиц                 |
| Переменные отчёта           | секция `variables` из `config.variables`                                                  |

```ts
interface QuerySelect {
  name: string;
  aggr: string;
  alias: string;
  id: string;
  fieldAlias: string;
  lvl?: number;
}

interface QueryObject {
  select: QuerySelect[];
  group: Omit<QuerySelect, 'aggr'>[];
  order: unknown[];
  where: QuerySelect[];
  having: QuerySelect[];
  options: { seriesAutoFill: boolean };
  limit?: number;
}

/** Порядок обхода полок: группирующие раньше значений — трейс собирается из накопленного. */
const AXE_ORDER: Record<string, number> = { series: -2, categories: -1 };

const toSelect = (field: ChartField, alias: string): QuerySelect => ({
  name: field.name,
  aggr: field.agg || '',
  alias,
  id: field.id,
  fieldAlias: field.title || field.alias || field.name,
});

// Сигнатура — как в заглушке шаблона и в ядре: `getQueryObjects(config, exportMode = null, settings = {})`.
// Два последних параметра нужны только экспортным режимам; сужать сигнатуру до одного аргумента нельзя.
static getQueryObjects(config: ChartConfig, _exportMode: unknown = null, _settings: unknown = {}): QueryObject[] {
  const axes = [...(config?.axes || [])].sort(
    (a, b) => (AXE_ORDER[a.type] ?? 0) - (AXE_ORDER[b.type] ?? 0),
  );
  if (!axes.length) return [];

  const queryObjects: QueryObject[] = [];
  const selectGroup: QuerySelect[] = [];
  const group: QueryObject['group'][number][] = [];
  const where: QuerySelect[] = [];
  const options = { seriesAutoFill: false };

  for (const axe of axes) {
    const fields = axe.fields || [];
    // Индекс в алиасе появляется только у многопилюльной полки «Категории».
    const multiple = axe.type === 'categories' && axe.selectedFieldIndex === -2;

    fields.forEach((field, index) => {
      const alias = `[${axe.type}]${multiple ? `[${index}]` : ''}`;

      switch (axe.type) {
        case 'categories':
        case 'series': {
          selectGroup.push(toSelect(field, alias));
          if (!group.some((item) => item.name === field.name)) {
            const { aggr: _aggr, ...groupItem } = toSelect(field, alias);
            group.push(groupItem);
          }
          break;
        }

        case 'filters':
          where.push({ ...toSelect(field, alias), lvl: field.lvl || 0 });
          break;

        case 'values':
          // Трейс на каждую пилюлю: значение первым элементом, группирующие следом.
          queryObjects.push({
            select: [{ ...toSelect(field, '[values]'), lvl: field.lvl || 0 }, ...selectGroup],
            group,
            order: [],
            where,
            having: [],
            options,
            limit: config.rowsLimit,
          });
          break;

        default:
          break;
      }
    });
  }

  return queryObjects;
}
```

`remapData` в минимальном виде — свести трейсы в строки по индексу:

```ts
/** Метаданные пилюли, которые `aggregateBypass` дописал к строке; в `plotData` им не место. */
const META_KEYS = new Set(['name', 'id', 'ID', 'fieldName', 'fieldAlias', 'fieldTitle', 'traceKey', 'values']);

remapData(_config: ChartConfig): this {
  const traces = this.aggregated;
  this.plotData = [];
  if (!traces.length) return this;

  const rowCount = traces[0].length;
  for (let i = 0; i < rowCount; i += 1) {
    const row: PlotRow = {};
    for (const trace of traces) {
      const item = trace[i];
      if (!item) continue;

      // Измерения: categories, series, [categories][0]… — общие у всех трейсов.
      for (const [key, value] of Object.entries(item)) {
        if (!META_KEYS.has(key)) row[key] = value;
      }

      // Значение трейса — под `id` пилюли: он уникален, а имя с агрегацией у двух
      // одинаковых пилюль совпадёт и второе значение затрёт первое.
      row[item.id] = item.values;
    }
    this.plotData[i] = row;
  }
  return this;
}
```

Перенос измерений — решение плагина, а не копия ядра: **штатный `remapData` их в `plotData`
не кладёт вовсе**, только значения, `identity`/`linkage` и служебные `thresholds`, `keyString`,
`__info`. Поэтому часть плагинов читает категории не из `plotData`, а напрямую из
`aggregated[0]` — и это законный вариант. Выбирай осознанно: нужны категории и значения в одной
строке — переноси, как выше; хватает трейсов — можно не собирать `plotData` вовсе, но тогда
`CustomChart` должен читать `adaptor.aggregated`.

Метаданные пилюли (`name`, `id`, `fieldAlias`, `traceKey`) в строку трейса кладёт
`aggregateBypass` — он же решает, разрезаны ли уже данные по трейсам.

## Грабли

| Симптом                                              | Причина                                                                                                |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Данных нет, запрос ушёл                              | `getQueryObjects` вернул `[]` — заглушка не заменена                                                   |
| `props.data` пуст, хотя ответ в сети пришёл          | `cacheId` передан шестым аргументом — ответ лёг в `props.datas[cacheId]`, читать оба места             |
| Тумблер «Автообновление» включён, данные прежние     | таймер перезапроса заводит плагин; ядро его не крутит, инжект — `reloadDatas`, а не `loadDatas`        |
| `row['[details]']` — `undefined`                     | такого алиаса нет: «Детали» уходят в запрос как `[values]`, то есть отдельным трейсом                  |
| `row.categories` — `undefined`, хотя полка заполнена | пилюль на полке несколько → ключ `[categories][0]`                                                     |
| Значения двух пилюль перезаписывают друг друга       | трейсы сведены по общему ключу `values`, а не по `elem.id` каждой пилюли                               |
| Один трейс вместо нескольких                         | `queryObjects` собран одним объектом; ядро ждёт по объекту на пилюлю значений                          |
| Группирующие поля не попали в трейс                  | полки обойдены в порядке конфига: `values` встретилась раньше `categories`                             |
| Дубли в `group`                                      | повтор по `name` не отсеян                                                                             |
| Фильтр не применился                                 | описание поля ушло в `where`, но значения ядро берёт из `config.filters` — третий аргумент `loadDatas` |
| `countd` не работает                                 | агрегацию нужно заменить на `count` + `distinct: 1`                                                    |
| Строк меньше, чем ожидалось                          | `limit` из `config.rowsLimit`, плюс обрезка по `rowsLimitToShow` в `refresh`                           |

## Проверка

`getQueryObjects` — статический метод без состояния, то есть чистая функция: тестируется
целиком, без портала и без моков (компонент и ядро зовут его одним аргументом, два остальных
имеют умолчания). Это самая ценная часть покрытия — спек фиксирует форму
запроса, которую иначе видно только в сетевой панели.

Цикл — `tdd`: `test-writer` пишет спеки на конфиг из полок, `implementer` реализует. Что
проверять: число трейсов равно числу видимых пилюль значений; алиасы и суффиксы индексов;
группирующие поля попали в каждый трейс; фильтры — в `where`, а вычисляемые с
`filterSqlType: 'having'` — в `having`; `countd` превратилась в `count` + `distinct`;
пустые полки дают пустой результат.

`remapData` тестируется от заранее записанного ответа — **снятого с портала**, а не
придуманного. Придуманный ответ проверяет догадку о форме, а не форму.

**Фикстуры в репозитории нет, и это осознанно.** Форма ответа, описанная выше, восстановлена по
бандлу ядра: она сходится сама с собой и проверена грепом, но живым наблюдением не является.
Снимать образец сейчас не с чего — пока `getQueryObjects` заглушка, запрос уходит пустым.

Поэтому снятие фикстуры — **первый шаг того прохода, в котором пишется `remapData`**, а не
задача «когда-нибудь»:

1. `npm start` поверх распакованного `prebuild/`, отчёт с заполненными полками — минимум две
   пилюли на «Значениях» и две на «Категориях», иначе не проверишь ни трейсы, ни суффиксы;
2. `console.log(JSON.stringify(data?.data, null, 2))` в `CustomChart` до сборки адаптора;
3. результат — JSON-файлом рядом со спеком, и уже от него пишется тест.

До этого шага `remapData` тестом не покрывается: зелёный тест на сочинённых данных хуже
отсутствующего — он создаёт уверенность, которой нечем подкрепиться. Если снять образец нельзя
(нет доступа к порталу), так и скажи пользователю и останови проход, а не заменяй фикстуру
выдумкой.
