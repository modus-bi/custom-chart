# Перевод плагина на TypeScript

Работа идёт в **чужом** репозитории — плагине пользователя, а не в шаблоне. Шаблон здесь только
образец: каждый файл конфигурации уже написан и лежит в `main` этого репозитория, изобретать его
заново не нужно.

Пошаговый рецепт с готовыми конфигурациями — [MIGRATION.md](../../../MIGRATION.md), раздел
«Перевести существующий плагин на TypeScript». Этот скилл задаёт порядок работы и то, чего делать
нельзя; содержание конфигураций — там.

## Главное правило

**Плагин остаётся собираемым после каждого шага.** Миграция постепенная: `allowJs: true` +
`checkJs: false` в `tsconfig.json` и два правила `swc-loader` в webpack позволяют держать `.js`
и `.ts` рядом. Перевод «всё за один проход» запрещён — он даёт сотню ошибок типов разом, и
разобрать, какая из них настоящая, уже невозможно.

## Порядок

### 1. Выясни, с чего начинаем

```bash
git log --oneline -5
ls src
cat package.json
```

Три возможных состояния, и они требуют разного:

- **Инструменты старые** (Babel, webpack 4, нет `tsconfig.json`) — начинай с шага 2.
- **Инструменты уже новые, код на `.js`** — переходи к шагу 4.
- **Половина файлов уже `.ts`** — шаг 4 для следующего файла, не трогая переведённые.

### 2. Согласуй объём с пользователем

Миграция затрагивает сборку, тесты, линт и формат — это не та правка, которую делают молча.
Спроси и дождись ответа:

- переводим весь плагин или только начинаем цепочку;
- прогонять ли `prettier --write` по всему репозиторию (Prettier 1 → 3 меняет умолчания и
  переформатирует почти всё) — если да, это **отдельный коммит** до перевода файлов;
- есть ли у плагина свои зависимости, которых нет в шаблоне, — их типы придётся ставить отдельно.

### 3. Перенеси инструменты

По шагам 1–7 из MIGRATION.md, в том же порядке. Каждый файл конфигурации бери из `main`
шаблона, а не пиши по памяти:

```bash
cat tsconfig.json swc.config.js jest.config.js webpack.config.js eslint.config.js
```

Контрольная точка: `npm run build` собирает бандл, плагин при этом целиком на JavaScript.
Не прошло — чини до перехода к коду.

### 4. Переводи по одному файлу

Порядок — снизу вверх (список в MIGRATION.md, «Порядок перевода файлов»): хелперы, конфиг,
адаптор и генератор спеки, `CustomAxes`, компоненты, редьюсер, `src/index.ts` последним.

На каждый файл:

1. `git mv foo.js foo.ts` (или `.jsx` → `.tsx`) — переименование отдельной командой сохраняет
   историю файла.
2. Расставь типы. Формы контракта — из `prebuild/api/chartPlugin.d.ts`, формы конфига — из
   `defaultConfig.json` этого плагина, а не из шаблонного.
3. `npm run typecheck && npm run build`.
4. Есть тесты — `npm test`.

Зелено — файл готов, берись за следующий. Правила языка (именование, где объявлять типы,
запрет на `any`) — скилл `typescript-coding-standards`, он вызывается автоматически.

### 5. Закрой миграцию

Когда `.js` в `src/` не осталось:

- убери `allowJs` и `checkJs` из `tsconfig.json`;
- убери правило `.m?jsx?$` из `webpack.config.js`;
- добавь `src/types/chartPlugin.d.ts` и `ContractCheck` в `src/index.ts`, если их ещё нет.

После этого случайно добавленный `.js` перестанет собираться молча.

## Чего делать нельзя

Перевод типизации — ровно та работа, где соблазн заглушить ошибку максимален, а цена заглушки
максимальна: она переживёт миграцию и останется в коде навсегда.

- **Не гасить ошибку через `any`, `as`, `@ts-expect-error`, `eslint-disable`.** Ошибка типа при
  переводе почти всегда означает, что настоящая форма данных отличается от предполагаемой.
  Смотри форму: `prebuild/api/chartPlugin.d.ts`, `defaultConfig.json`, печать реального ответа
  бэкенда.
- **Не переводить несколько файлов одним проходом.** Если ошибок больше десятка — откатись
  (`git checkout -- <файл>`) и возьми один файл.
- **Не менять поведение заодно с типами.** Рефакторинг во время перевода делает диагностику
  невозможной: непонятно, сломал типовой перевод или переписанная логика. Отдельным проходом,
  после зелёного прогона.
- **Не трогать `prebuild/`** — каталог перезаписывается при обновлении ядра, правка исчезнет.
- **Не переименовывать имя UMD-библиотеки и плейсхолдер** `CustomChart0` / `CustomChartNNN`.

Три правки одного места без зелёного прогона — стоп и разбор по правилу «Когда правки
зацикливаются» из CLAUDE.md, а не четвёртая правка.

## Отчёт

Назови: какие файлы переведены, какие остались на `.js`, что показали `npm run typecheck`,
`npm test` и `npm run build`, и какие места пришлось типизировать по догадке — их пользователь
должен проверить сам.
