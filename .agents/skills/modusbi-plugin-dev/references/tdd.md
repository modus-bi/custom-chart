# TDD и проверка результата

Для изменения поведения и исправления багов: требование → RED → GREEN → REFACTOR → проверки.
Один агент может выполнить весь цикл. Сабагенты — только если делегация отдельно разрешена
в текущей сессии; скилл не требует отдельной модели, функции Skill или инструмента Task.

## Последовательный цикл

1. Зафиксируй проверяемое требование и сценарии из SKILL.md. Сначала изучи действующие спеки.
2. RED: добавь минимальный тест на поведение или воспроизведение бага. Запусти локальный Jest
   с точным путём: `npm test -- --runInBand --runTestsByPath <путь-к-спеку>`.
   Прочитай причину падения: неправильный импорт/фикстура — ошибка теста; отсутствие именно
   нового согласованного API может быть ожидаемым RED. Не считай любой красный вывод успехом.
3. GREEN: реализуй поведение, сохраняя смысл теста. Если ожидание противоречит требованию,
   разберись с источником противоречия; меняй ошибочный тест с объяснением, не ради зелёного.
4. Прогони связанный набор и полный набор; рефакторинг выполняй на зелёном состоянии.
5. Явно выполни typecheck, lint и нужную сборку. Нет автоматического post-edit typecheck.
6. Проверь контракт/настройки по тематическим справочникам при соответствующих изменениях.

При первой настройке тест редьюсера-заглушки действительно меняется: он больше не должен
ждать неизменное состояние для новой известной команды. Проверку неизвестной команды сохрани.
Для документации, косметической правки или поведения, которое уже покрыто подходящим тестом,
не создавай дублирующий тест только ради процедуры.

## Роли при разрешённой делегации

| Роль | Область | Передача результата |
| --- | --- | --- |
| test-writer | Только `*.spec.{js,jsx,ts,tsx}` и необходимые `test/**` | Требование, пути, фактический RED и причина |
| implementer | Реализация/конфигурация в согласованном объёме, без спеков/test | Изменения, GREEN, typecheck/lint/build |
| contract-reviewer | Чтение и проверки, без правок | Находки по sync-contract |
| settings-flow-reviewer | Чтение и проверки, без правок | Находки по new-setting/custom-reducers |

Это границы заданий, не технические ACL. Последовательные RED/GREEN зависят друг от друга;
их не запускают одновременно. Основной агент проверяет артефакты и результаты сам.

## Моки не должны менять API

Компонентные спеки: `/** @jest-environment jsdom */`, React classic, Testing Library React 12
для React 16. `pluginImports`, `autoApplySettings`, `loadDatas` — удобные границы моков.
Не мокай весь проверяемый модуль вместо его поведения.

Мок тумблера должен принимать `toggled` и звать `onToggle(event, boolean)`:

```tsx
const SettingsToggle = ({ toggled, onToggle }: {
  toggled: boolean;
  onToggle: (event: unknown, value: boolean) => void;
}) => (
  <input type='checkbox' checked={toggled}
    onChange={(event) => onToggle(event, event.target.checked)} />
);
```

HTML input здесь — реализация мока. Публичные props имитируют ядро, а не checked/onChange
самого input. Для numeric-поля сохраняй второй аргумент callback и учитывай задержку ядра.
Подставляй ResizeObserver/structuredClone только когда тест действительно нуждается в них;
JSON-копия не подходит для Date/undefined/циклов/Map и не доказывает полноценное клонирование.

Проверяй поведение: команда и значение; отсутствие мутации; обязательный autoApplySettings;
create/render/resize/destroy и отписка; чистый buildSpec; форма данных по реальной обезличенной
фикстуре. Синтетические крайние случаи допустимы как unit-тесты и помечаются синтетическими,
но не подтверждают форму реального ответа ядра.

В финале различай автоматические проверки и [портальный прогон](portal-integration-testing.md).
Не обещай фиксированное время тестов и не считай `--passWithNoTests` доказательством покрытия.
