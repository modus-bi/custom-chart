# Модуль CustomReducers

## Суть

Модуль — одна функция: обработчик действия `CHANGE_CUSTOM_CHART_N`, которое ядро отправляет,
когда пользователь трогает настройку в правой панели. Всё, что он делает, — кладёт значение
по нужному пути в черновик конфига и отдаёт состояние ядру.

Из-за размера модуля кажется, что правил тут не нужно. Нужны: три из них нарушаются регулярно
и каждый раз стоят часа отладки, потому что отказ выглядит как «настройка просто не работает».

## Устройство

```
src/modules/CustomReducers/
  changeCustomChartReducer.ts        обработчик и таблица команд
  changeCustomChartReducer.spec.ts   спек рядом
```

Разрастаться модулю не с чего: команды добавляются строками в таблицу, а не файлами. Если
понадобился второй файл — это либо чистый хелпер работы с данными (тогда `CustomChart/lib/`,
а не здесь), либо признак, что в редьюсер поехала логика, которой там не место.

Хелперы **панели настроек** (`getSectionConfig` и общие пункты вроде `NumberSettingItem` — см.
`new-setting`) сюда тоже не едут: их место в `src/modules/CustomSettings/`, рядом с секциями,
которые их зовут. Редьюсер про панель не знает — он знает про команду и путь в конфиге.

Приведение значения к типу конфига — тоже не сюда: строку в число превращает пункт панели, до
вызова `changeChart`. Таблица команд кладёт значение по пути **как есть**.

## Три правила

### 1. Таблица команд вместо ветвлений

Соответствие «команда → путь в конфиге» хранится **таблицей**, а не цепочкой `if` или
`switch`. Новая настройка добавляется одной строкой, и это единственное место, где команда
упоминается в редьюсере.

```ts
/** Вложенные поля конфига пишутся через точку. */
export const COMMANDS: Record<string, string> = {
  TOGGLE_LEGEND: 'legend.visible',
  CHANGE_CATEGORY_AXIS_FONT_SIZE: 'categoryAxis.fontSize',
};
```

Неизвестная команда — возврат состояния без изменений, а не исключение: ядро шлёт в редьюсер
плагина и свои действия, падать на них нельзя.

Ветвление в редьюсере появляется только тогда, когда команде мало «положить значение по пути»
— например, одна настройка меняет два поля. Такой случай — повод сначала спросить себя, не
проще ли отправить из панели две команды.

### 2. Черновик копируется, а не правится на месте

Правится `state.component.configDraft`, и правится **копия**:

```ts
const configDraft = structuredClone(state.component.configDraft);
setByPath(configDraft, path, action?.settings?.value);

const nextState = {
  ...state,
  component: { ...state.component, configDraft },
};
```

Мутация исходного объекта ломает сравнение по ссылке в ядре: React не увидит изменения, и
настройка «не сработает» через раз — самый неприятный вид отказа, потому что воспроизводится
не всегда.

Клонировать — `structuredClone`, не `_.cloneDeep`. Конфиг — чистые данные, а рантайм-зависимостей
у шаблона нет вовсе. **`react-addons-update` не использовать**: пакет заброшен, официально
заменён на `immutability-helper` и тянет legacy-обвязку React. Встретишь в коде, скопированном
из ядра, — убирай: неглубокие правки делаются спредом, глубокие — клонированием.

### 3. Результат обязан пройти через `autoApplySettings`

```ts
return options.autoApplySettings(nextState);
```

Это **функция ядра, а не флаг**. Без неё правка осядет в `configDraft` и не доедет до
компонента: в панели значение изменилось, на диаграмме — нет. Она же учитывает режим ручного
применения (`manualApplySettings`) — помечает черновик как dirty вместо немедленного
применения, и без неё кнопка «Применить» перестаёт что-либо значить.

Возврат `nextState` напрямую — самая частая ошибка модуля.

**Что она делает с состоянием** (по бандлу ядра, `coreVersion 3.16.3`): ставит `configDraft.dirty = true`, а в автоматическом режиме (`manualApplySettings` ложно) снимает `dirty`, ставит `configDraft.unsaved = true` и подменяет `component.config` результатом `prepareAxes(configDraft)`. Состояние она **мутирует и возвращает тот же объект**, нового не создаёт — именно поэтому копию черновика обязан сделать редьюсер до вызова, а не она.

Практическое следствие для тестов: после настоящей `autoApplySettings` в черновике появляются служебные `dirty` и `unsaved`, которых нет в `ChartConfig`. Строгое `toEqual` на весь `configDraft` сломается — сверяй конкретный путь. В спеке функция всё равно подставляется как `jest.fn((s) => s)`, так что этих полей там не будет; знать про них нужно при разборе поведения на портале.

## Запись по пути

Путь из таблицы разбирается по точкам, отсутствующие узлы создаются:

```ts
const setByPath = (target: Record<string, unknown>, path: string, value: unknown): void => {
  const keys = path.split('.');
  const last = keys.pop() as string;
  const parent = keys.reduce<Record<string, unknown>>((node, key) => {
    if (typeof node[key] !== 'object' || node[key] === null) node[key] = {};
    return node[key] as Record<string, unknown>;
  }, target);
  parent[last] = value;
};
```

Создание отсутствующих узлов — не удобство, а обязательное поведение: отчёт, сохранённый до
появления настройки, не содержит её ветки конфига вовсе, и без этого правка в таком отчёте
упала бы.

## Что в редьюсер не кладут

| Чего не делать                                  | Куда это на самом деле                                           |
| ----------------------------------------------- | ---------------------------------------------------------------- |
| Пересчёт данных, обращение к адаптору           | `dataAdaptor.ts` — редьюсер знает только про конфиг              |
| Валидация значения настройки                    | в компонент панели: не давать ввести неверное, а не чинить после |
| Значения по умолчанию для новой настройки       | `model/defaultConfig.json` и тип `ChartConfig`                   |
| Побочные эффекты: запросы, таймеры, логирование | никуда: редьюсер обязан оставаться чистой функцией               |
| `console.log` в отлаженном коде                 | убрать: редьюсер зовётся на каждое движение слайдера             |

## Тесты

Редьюсер — чистая функция трёх аргументов, тестируется целиком без DOM и без портала. Это
самая дешёвая проверка во всём плагине, и покрывать её нужно полностью:

- известная команда кладёт значение по своему пути;
- неизвестная команда возвращает состояние **тем же объектом**;
- исходный `configDraft` не изменился (проверка на мутацию);
- путь с отсутствующими промежуточными узлами создаётся;
- `autoApplySettings` вызван ровно один раз и его результат возвращён.

Последний пункт проверяется подстановкой `options.autoApplySettings` как `jest.fn((s) => s)` —
и именно он ловит ошибку, которая иначе видна только на портале.

## Смежные скиллы

- `new-setting` — полная цепочка заведения настройки: пункт панели, команда, строка в таблице,
  поле в `ChartConfig`, дефолт в конфиге;
- `custom-chart-module` — где живут типы и дефолты, которые правит эта работа.
