# Конвенции TypeScript

## Область действия

| Где                                                                                           | Применяется                                                                                                                 |
| --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `src/modules/**`, `src/managers/`, `src/index.ts`                                             | Да, это весь TypeScript проекта                                                                                             |
| `src/types/**`                                                                                | Только именование; файлы целиком состоят из деклараций, `chartPlugin.d.ts` вообще не пишется руками (скилл `sync-contract`) |
| `prebuild/**`                                                                                 | **Нет.** Распакованное ядро, каталог перезаписывается                                                                       |
| Корневые конфиги (`webpack.config.js`, `jest.config.js`, `swc.config.js`, `create-plugin.js`) | Нет, это CommonJS                                                                                                           |

## Что делают инструменты, а не ты

Prettier — единственный источник истины по форматированию: 2 пробела, 120 колонок, одинарные кавычки в том числе в JSX, точки с запятой, trailing commas везде, по одному JSX-атрибуту на строку. Отступы и переносы вручную не выравнивай — `prettier --write` идёт на pre-commit через lint-staged.

ESLint 10 (flat config, [eslint.config.js](../../../eslint.config.js)) — `@eslint/js` + `typescript-eslint` recommended, `eslint-config-prettier` последним звеном.

`tsc --noEmit` со `strict: true` висит на PostToolUse-хуке: после правки `.ts`/`.tsx` ошибки типов вернутся сразу.

Оставшиеся разделы — про то, чего эти три инструмента не проверяют.

## 1. Правила, нарушение которых ломает сборку

Это не стиль. Каждый пункт роняет бандл или рантайм плагина.

**`import type` для всего, что нужно только на этапе типов.**

```ts
import type { PluginConfig, PluginInjectedProps } from '../../types/chartPlugin';
```

В проекте `isolatedModules: true` и сборка через swc: каждый файл транспилируется отдельно, стереть тип-импорт по анализу использования компилятор не может. Обычный `import` типа остаётся в выводе как рантайм-импорт несуществующего модуля.

**`import React` в каждом `.tsx`.** JSX собирается в classic runtime (`jsx: "react"`). Automatic runtime подтянул бы `react/jsx-runtime`, которого нет в `externals` — он уехал бы в бандл и разошёлся с React ядра. Правило живёт в [swc.config.js](../../../swc.config.js), менять его не нужно.

**Никаких новых рантайм-зависимостей без обсуждения.** В `externals` только `react` и `react-dom` — их даёт ядро. Всё остальное, что импортируется как значение, попадает в единый UMD-бандл и увеличивает его — библиотеку отрисовки и любой другой пакет добавляй только осознанно.

Согласованное исключение одно: **`dompurify`** — им очищается HTML описания на обороте компонента (скилл `chart-shell`). Обсуждение по нему уже состоялось, отдельно спрашивать не нужно.

**UI-примитивы не импортируются.** Компоненты интерфейса приходят из ядра через проп `pluginImports` (`.components`, `.sections`, `.services`). Прямого импорта UI-кита в плагине нет и быть не должно.

## 2. Именование

| Что                      | Как                                  | Пример из проекта                     |
| ------------------------ | ------------------------------------ | ------------------------------------- |
| Переменные, функции      | `camelCase`                          | `applyCommand`, `getDefaultConfig`    |
| Классы, интерфейсы, типы | `PascalCase` без префиксов `I` и `T` | `ComponentTypeManager`, `ChartConfig` |
| Константы модуля         | `UPPER_SNAKE_CASE`                   |                                       |
| Внутренние члены класса  | `_camelCase`                         |                                       |
| Дженерики                | `T`, `K`, `V`, `E`                   |                                       |

Своих `_`-членов класса в шаблоне нет — только ведущее подчёркивание у намеренно неиспользуемых параметров методов-заглушек (`_config`, `_axisName`…), см. пример в блоке правил `@typescript-eslint/no-unused-vars` в `eslint.config.js`. Это отдельная, более узкая конвенция: не «внутренний член», а «параметр контрактной сигнатуры, который эта реализация не читает».

Проектное:

- **Setting item** — если пункт настройки заведён отдельным компонентом (оправдано только при собственном состоянии — см. скилл `new-setting`), каталог и файл одного имени вида `<Что><Контрол>SettingItem`: например `ColorSettingItem`, `RangeSettingItem`. Каждому компоненту — `displayName`.
- **Секция настроек** — `<Что>Section`, файл в `src/modules/CustomSettings/sections/`: в шаблоне пока нет ни одной, образец именования — скилл `new-setting`.
- **Команда `changeChart`** — `UPPER_SNAKE_CASE`, отражающая действие и путь в конфиге: условный пример — `TOGGLE_LEGEND` (пишет в `legend.visible`), см. скилл `new-setting`.
- **Тексты интерфейса** — русские строковые литералы прямо в JSX, без словаря.

## 3. Типизация

**`any` не используем.** Граница с ядром типизируется `unknown` с последующим сужением — так типизированы параметры заглушек `dataAdaptor.ts` (`_data: unknown`, `_spec: unknown`) и `ComponentTypeManager.getDataAdaptor`. Причина не в стиле: контракт `chartPlugin.d.ts` намеренно объявляет `config`, `field`, `axe`, `spec`, `data` как `any`-псевдонимы, потому что в ядре они на нетипизированном JS. Наш `unknown` — это явная отметка «форма неизвестна, сузь перед использованием», тогда как `any` тихо гасит проверки на всём пути.

Сужай локально, ближе к использованию:

```ts
const configNew = structuredClone(config) as ChartConfig;
```

**`interface` для формы объекта и контрактов классов, `type` для объединений, пересечений, мапленых и вспомогательных типов.**

```ts
interface OutlineConfig {
  color: string;
  enabled: boolean;
  width: number;
}

export type ChangeChart = (command: string, settings: { value: unknown }) => void;
```

**Необязательное поле — `?`, отсутствие значения — явный union с `null`.** Значения из конфига отчёта часто приходят `null` (`config.balloonTemplate`), а не `undefined` — не путай эти два случая.

**Явный возвращаемый тип** — у экспортируемых функций и везде, где вывод неочевиден. У стрелочных компонентов возвращаемый тип не пишем: он выводится и только шумит.

## 4. Где живут типы

Правило зависит от **роли типа**, а не от того, сколько их в файле.

| Роль типа                                                                           | Где объявлять                                                                                                   |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Props одного компонента                                                             | Рядом, в файле компонента. Это часть его сигнатуры                                                              |
| Общие типы панели настроек (`ChangeChart`, тип props секции)                        | `src/modules/CustomSettings/types.ts` (заводится вместе с первой секцией — см. скилл `new-setting`)             |
| **Форма данных**: `config`, `configDraft`, строки данных для отрисовки (`plotData`) | Отдельный `<имя>.types.ts` рядом с модулем — пример из проекта: `src/modules/CustomChart/model/plugin.types.ts` |
| Снимок контракта ядра                                                               | `src/types/chartPlugin.d.ts`. Руками не пишется — переносится скиллом `sync-contract`                           |

**Порог выноса: тип понадобился второму модулю или тесту — выноси.** Форма данных пересекает границы модулей по определению (редьюсер пишет `configDraft`, компонент читает `config`, адаптер строит `plotData`), поэтому для неё правило безусловное. Props компонента не покидают его файл, и вынос ради выноса только добавляет прыжок между файлами.

Пример выноса — форма конфига (из проекта, `src/modules/CustomChart/model/plugin.types.ts`):

```ts
// plugin.types.ts
export interface OutlineConfig {
  color: string;
  enabled: boolean;
  width: number;
}

export interface ChartConfig {
  outline: OutlineConfig;
  // …
}
```

```ts
// dataAdaptor.ts
import type { ChartConfig } from './plugin.types';
```

Существующий код под это правило задним числом не переписывай. Переноси форму данных в `.types.ts` тогда, когда всё равно правишь этот модуль и тип уже понадобился кому-то ещё.

## 5. Функции и классы

До трёх аргументов; дальше — объект-параметр. Компоненты и так принимают один объект props — там вопрос не возникает.

Значения по умолчанию — в сигнатуре, не через `||` в теле.

Стрелочные `const` — форма модульных хелперов (`const applyCommand = (...) => {...}`); компоненты шаблона объявлены через `function` (`CustomChart`, `Settings`) — им дописываются `displayName` и, у `CustomChart`, статический `getDefaultConfig`. Обе формы допустимы; существующие объявления не переписывай.

Классы в TS-части — минимум: только там, где сигнатура контракта ядра требует класс (конструкторы `DataAdaptor`, `SpecGenerator`, `ConfigEditor`) и `ComponentTypeManager`. Два исключения среди компонентов согласованы заранее: **граница ошибок** (в React 16 `componentDidCatch`/`getDerivedStateFromError` бывают только у классов — скилл `chart-shell`) и **владелец инстанса библиотеки отрисовки**, если фазы `componentDidMount`/`componentDidUpdate`/`componentWillUnmount` читаются прямее, чем те же фазы в эффектах с `ref` (скилл `chart-lifecycle`). Второе — выбор, а не обязанность; функциональная форма с хуками остаётся штатной. Порядок членов: поля → конструктор → методы. Внутренние методы с `_`. Модификаторы доступа существующие классы не используют; в новом коде указывай их явно, но задним числом по проекту не расставляй.

## 6. Импорты

Порядок с пустой строкой между группами:

```ts
import React, { useEffect } from 'react';

import type { PluginConfig, PluginInjectedProps } from '../../types/chartPlugin';

import { getDefaultConfig } from './model/getDefaultConfig';
import { useChartSize } from './hooks/useChartSize';
```

1. внешние пакеты;
2. `import type` — вся типовая часть одной группой;
3. внутренние модули как значения;
4. стили (`import './Component.scss'`).

Алиасов и нестандартного резолва в проекте нет — все внутренние импорты относительные. Стили — обычный SCSS, не CSS-модули.

## 7. Структура модуля

```
sections/
  <Что>Section.tsx                     секция
  <Что>Section.spec.tsx                тесты рядом
  ColorSettingItem/                    компонент заводится, только если пункту нужно состояние
    ColorSettingItem.tsx
    ColorSettingItem.scss              стили, имя совпадает с компонентом
    ColorSettingItem.spec.tsx
```

`index.ts` заводим только там, где он реально нужен как точка входа: у модуля — да (`src/modules/CustomChart/index.ts` — публичный контракт модуля, `src/modules/CustomAxes/index.tsx` — сам объект осей), у подпапки модуля (`model/`, `ui/`, `hooks/`, `lib/`, `engine/`) — нет. Разбор правила — скилл `custom-chart-module`.

Тесты — `*.spec.{ts,tsx}` рядом с кодом. Компонентный спек открывается docblock'ом `/** @jest-environment jsdom */`: глобальное окружение jest — `node`. Процесс написания — скилл `tdd`; правила этого скилла на спеки распространяются полностью, `import type` и `import React` в них так же обязательны.

Глобальные типы jest подключены через `types: ["jest"]` в [tsconfig.json](../../../tsconfig.json): без этого поля `tsc` падает на `describe` с `TS2593`. Указание `types` отключает автоподключение остальных `@types/*`, поэтому новый пакет с глобальными объявлениями надо дописывать в этот массив вручную. На типы, импортируемые явно (`@types/react`), это не влияет.

## 8. Комментарии

Комментарии на русском, как весь остальной текст в проекте.

JSDoc — там, где контракт неочевиден: почему функция не мутирует вход, что означает возвращаемый `null`, какое поведение ядра подразумевается. Особенно ценен на границе с ядром, потому что типы там `unknown`, и смысл поля больше взять неоткуда.

Не пересказывай код. `// увеличиваем счётчик` над `count++` — шум.

**Комментарий описывает код в его нынешнем виде — и только это.** Истории изменений в комментариях нет: «раньше здесь наследовался…», «копия удалена», «этот метод переписали, потому что…», «решение владельца» — всё это принадлежит истории репозитория, а не файлу. Такой текст стареет молча: код меняется дальше, а комментарий продолжает рассказывать про позапрошлое состояние, и читатель верит ему.

Практическое правило: если из комментария выкинуть все глаголы прошедшего времени и он перестаёт иметь смысл — комментарий описывает историю, а не код. Заглушка объясняется через то, что она делает и что должна делать реализация («метод возвращает пустой массив; полная реализация собирает запрос из полок конфига»), а не через то, что было на её месте.

То же касается сравнений с отвергнутыми вариантами. «Условный тип здесь не работает, поэтому взяли ограничение параметра» — рассказ о выборе; «ограничение параметра проверяется компилятором при каждом инстанцировании» — свойство кода. Пиши второе.

## Чеклист ревью

- `import type` для всех типовых импортов; `import React` на месте в каждом `.tsx`;
- новых рантайм-зависимостей не появилось;
- `any` отсутствует, граница с ядром на `unknown` с сужением;
- `interface` для формы объекта, `type` для объединений и алиасов;
- форма данных вынесена в `.types.ts`, props компонента остались рядом с ним;
- именование setting item / секции / команды `changeChart` совпадает с соседями;
- порядок импортов: внешние → типы → внутренние → стили;
- у компонента есть `displayName`;
- `npm run typecheck` и `npm run lint` зелёные.
