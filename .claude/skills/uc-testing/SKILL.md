# Тестирование по UC

## Суть

Прогон и правки — **разные фазы, и они не смешиваются**. Правка посреди прогона делает
результат недостоверным: часть пунктов проверена на одной сборке, часть на другой, и что
именно сломано, восстановить уже нельзя.

Шесть фаз, каждая заканчивается артефактом:

| #   | Фаза                                     | Артефакт                                                    |
| --- | ---------------------------------------- | ----------------------------------------------------------- |
| 1   | UC по требованиям задачи                 | `docs/uc-<фича>.md`                                         |
| 2   | Прогон без правок                        | `docs/uc-runs/<дата>-<фича>.md`                             |
| 3   | Разбор багов                             | список багов + вопросы пользователю, если есть противоречия |
| 4   | Правки по правилам проекта               | коммиты                                                     |
| 5   | Повторный прогон только по правкам       | дописанный журнал того же прогона                           |
| 6   | Саммари и предложение повторного прогона | ответ пользователю                                          |

Среду поднимает скилл `portal-integration-testing` — он же держит матрицу интеграции,
обязательную для любого плагина. Этот скилл добавляет к ней **процесс**: откуда берутся
проверки, как ведётся прогон, что делается с найденным.

## Гейт: без этого прогон не начинается

Проверяется до первого клика, всё разом:

1. **Среда поднята** — ядро в `prebuild/` с подставленным конфигом, `npm start` работает,
   отчёт-полигон использует компонент типа `CustomChart0`. Детали — `portal-integration-testing`.
2. **Playwright MCP доступен.** Прогон идёт через него, а не через встроенный браузер: только
   так остаются воспроизводимые шаги, консоль и сетевые запросы. Сервер объявлен в `.mcp.json`
   шаблона; недоступен — прогон не начинается, об этом сообщается пользователю.
3. **UC написан** — то есть пройдена фаза 1.

Отдельно — **подготовка отчёта-полигона**. Воспроизводимой она становится только тогда, когда
данные и компонент заводятся через API портала, а не кликами: иначе расхождение «у меня
получилось иначе» потом не разбирается. В шаблоне для этого ничего не подключено — в `.mcp.json`
только `playwright`. Отсюда две дороги:

- **MCP-сервер `modusbi` подключён** (проверяется явно: `ToolSearch: select:mcp__modusbi__report_operations,mcp__modusbi__component_crud`)
  — готовить полигон только через него;
- **не подключён** — готовить руками через UI **можно**, но в шапке журнала прогона пишется
  отдельной строкой: «полигон подготовлен вручную, шаги подготовки невоспроизводимы». Эта
  пометка нужна не для отчётности: она объясняет, почему повторный прогон может не сойтись с
  первым, и не даёт списать расхождение на код.

Тихо подменять первое вторым нельзя. Пользователю сообщается, каким путём пошли, до начала
прогона, а не в саммари.

## Фаза 1. UC по требованиям задачи

**UC рождается из требований, а не из кода.** Читать реализацию, чтобы понять, что проверять, —
значит проверять, что код делает то, что делает.

Источник — постановка задачи и согласованные требования. Пробел в постановке закрывается
вопросом пользователю, а не догадкой: правило CLAUDE.md «Требования не выдумываются» действует
здесь полностью, включая пять полей требования (вход, ожидаемое поведение, пустые данные,
ошибка запроса, сохранённый конфиг). Три последних поля в задачах не пишут почти никогда — и
именно они дают самые частые падения на портале, поэтому в UC они попадают всегда.

Файл — `docs/uc-<фича>.md`. Форма: разделы по темам, внутри — пункты-чекбоксы.

Требования к пункту:

| Требование                 | Плохо                            | Хорошо                                                                    |
| -------------------------- | -------------------------------- | ------------------------------------------------------------------------- |
| Один наблюдаемый результат | «Легенда работает»               | «Положение «Слева» переносит легенду влево, диаграмма на неё не наезжает» |
| Проверяемо глазами или DOM | «Стало удобнее»                  | «Поверх холста полоса «Показаны не все категории»»                        |
| Без ссылки на внутренности | «`buildSpec` вернул `truncated`» | «Полоса о лимите видна»                                                   |

Известное ограничение ядра или бэкенда пишется в UC **отдельным пунктом с пометкой**, а не
выкидывается: пункт остаётся, чтобы его перепроверили, когда ограничение снимут.

## Фаза 2. Прогон

**Правил ровно одно, и оно жёсткое: во время прогона код не правится.** Ни строчки — ни в
плагине, ни в конфиге, ни в сборке. Нашёл баг — записал и пошёл дальше.

Вход в портал: логин и пароль вводит **пользователь сам**. Агент открывает страницу входа и
останавливается; учётные данные не вводит, не запрашивает и не хранит.

Журнал прогона — `docs/uc-runs/<ГГГГ-ММ-ДД>-<фича>.md`, отдельный файл на каждый прогон.
Отметка на каждый пункт UC, без пропусков:

| Отметка        | Когда                                          |
| -------------- | ---------------------------------------------- |
| Пройден        | Наблюдаемый результат совпал с ожидаемым       |
| **Не пройден** | Не совпал — заводится баг, номер пишется рядом |
| Не проверено   | Проверить не удалось — обязательно с причиной  |

Что кладётся в журнал по ходу, а не восстанавливается по памяти в конце: снимок экрана на
каждый непройденный пункт, ошибки консоли, запросы сети, если они относятся к делу.

**Блокирующий баг останавливает прогон.** Блокирующий — тот, после которого проверять нечего:
плагин не грузится, отчёт не открывается, данные не приходят вовсе. Оставшиеся пункты
помечаются «не проверено — блокер <номер>», прогон закрывается, дальше — фаза 3 по тому, что
успели. Гнать прогон по заведомо сломанной сборке бессмысленно: непройденные пункты будут
следствием блокера, а не самостоятельными багами.

## Фаза 3. Разбор багов

Каждый баг описывается одинаково — иначе его не воспроизвести ни через день, ни другому агенту:

```markdown
### Б<номер>. <Что не так, одной строкой>

- **Пункт UC:** раздел и формулировка пункта
- **Ожидалось:** из UC
- **Фактически:** что наблюдалось
- **Шаги:** по действиям, с которых воспроизводится
- **Консоль и сеть:** ошибки или «чисто»
- **Серьёзность:** блокирующий / существенный / косметический
```

Дальше — **развилка, ради которой существует фаза**:

**Противоречие** — это когда неизвестно, каким поведение должно быть. Признаки:

- баг противоречит другому багу: исправление одного делает другой неисправимым;
- UC требует одного, требования задачи допускают другое прочтение;
- поведение упирается в ограничение ядра, и выбор — обходить его или принять;
- «правильно» зависит от продуктового решения, которого в постановке нет.

**Не противоречие** — очевидная поломка: не совпало с ясным требованием, ошибка в консоли,
падение, опечатка в тексте.

| Что нашли                        | Что делать                                                                                                                                                                                |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Противоречий нет ни в одном баге | Идти в фазу 4 сразу, вопросов не задавать                                                                                                                                                 |
| Есть хотя бы одно                | Собрать вопросы **по всем** таким багам разом, задать одним заходом — каждый с вариантами и своей рекомендацией, чтобы ответить можно было одним словом. Дождаться ответа и потом править |

Пока ждёшь ответа — делай ту часть правок, которая от него не зависит.

## Фаза 4. Правки

Правки идут **по правилам проекта**, а не «по-быстрому, раз всё равно уже нашли»:

- цикл `tdd` — сначала падающий тест, воспроизводящий баг, потом реализация;
- скилл по месту правки: `new-setting`, `custom-axes-module`, `custom-reducers-module`,
  `data-query-contract`, `chart-lifecycle`, `echarts-engine`, `chart-shell`,
  `number-formatting`;
- `typescript-coding-standards` — автоматически, перед любой правкой `.ts`/`.tsx`;
- зелёные `npm test`, `npm run typecheck`, `npm run lint` до повторного прогона.

Каждая правка помечается в журнале номером бага, который она закрывает.

## Фаза 5. Повторный прогон только по правкам

Полный UC заново **не гоняется**. Набор повторного прогона — ровно два множества:

1. пункты, на которых баги были найдены;
2. пункты, которых правка могла коснуться, — соседние настройки той же секции, тот же путь в
   конфиге, тот же участок отрисовки.

Второе множество определяется по диффу правок, а не по ощущению. Результат дописывается в тот
же файл журнала разделом «Повторный прогон <дата>» — так видно, что баг закрыт именно правкой,
а не пересозданием отчёта.

Баг не воспроизводится после правки, но и правка его не объясняет — это не «починилось»:
причина не найдена, баг остаётся открытым с пометкой «не воспроизводится».

## Фаза 6. Саммари

В ответе пользователю, коротко:

- сколько пунктов UC пройдено, сколько не пройдено, сколько не проверено и почему;
- баги списком: закрытые, открытые, отложенные с причиной;
- что осталось непроверенным и чего для этого не хватает;
- **предложение повторного полного прогона** — с ответом на вопрос, нужен ли он: нужен, если
  правки задели общий код, менялась сборка или блокер закрыл больше двух разделов UC.

Решение о повторном прогоне принимает пользователь; агент даёт рекомендацию, а не делает выбор
за него.

## Красные флаги — остановиться и вернуться в фазу

- «Тут правка на одну строчку, прогоню дальше уже с ней» — прогон стал недостоверным;
- «Этот пункт и так работал в прошлый раз» — непроверенный пункт помечается «не проверено»;
- «Похоже, тут имелось в виду вот это» — догадка вместо вопроса, фаза 1 или 3 не доделана;
- «Заведу баг после прогона, пока запомню» — снимок экрана и консоль потеряны;
- «UC напишу по коду, так быстрее» — проверка выродилась в пересказ реализации;
- «Полигон собрал руками, но писать об этом незачем» — гейт обойдён молча;
- «Прогоню весь UC заново, так надёжнее» — фаза 5 не про надёжность, а про адресность.

## Частые ошибки

| Симптом                                             | Причина                                                       |
| --------------------------------------------------- | ------------------------------------------------------------- |
| По журналу не восстановить, что именно сломалось    | Отметки ставились в конце по памяти, снимков нет              |
| Баг после правки «пропал», через день вернулся      | Причина не найдена, правка закрыла симптом                    |
| Половина непройденных пунктов оказалась одним багом | Прогон продолжили после блокера                               |
| Правки разъехались с ожиданиями пользователя        | Противоречия не вынесли в вопросы, решили за него             |
| Повторный прогон не поймал регресс                  | В набор взяли только пункты багов, соседние по диффу не взяли |
| Прогон нечем повторить на другой машине             | Полигон готовили руками, и в журнале об этом не сказано       |

## Смежные скиллы

- `portal-integration-testing` — среда, матрица интеграции, что вообще проверяется в портале;
- `tdd` — цикл, по которому идут правки фазы 4;
- `package-plugin` — если по итогам прогона собирается дистрибутив.
