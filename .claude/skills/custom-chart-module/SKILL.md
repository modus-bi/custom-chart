# Раскладка модуля CustomChart

## Суть

`CustomChart` — единственный модуль плагина, который растёт неограниченно: в нём и компонент,
и данные, и подложка, и интеграция с библиотекой отрисовки. Без раскладки он за месяц
превращается в два десятка файлов в одной папке, где `chartHelpers.ts` соседствует с
`chartUtils.ts`.

Правило раскладки одно и решает вопрос «куда класть» без обсуждений: **папку определяет род
файла, а не тема**. Тему видно из имени файла, род — нет.

Этот скилл — источник истины по раскладке модуля. Смежные (`chart-shell`, `chart-lifecycle`,
`echarts-engine`, `data-query-contract`) говорят, **что** написать; где этому лежать, решается
здесь. Разошлись — прав этот скилл, а расхождение стоит починить в том, другом.

## Структура

```
src/modules/CustomChart/
  index.ts               публичный контракт модуля: единственная дверь наружу
  CustomChart.tsx        компонент визуализации
  dataAdaptor.ts         ┐
  specGenerator.ts       ├ контрактные единицы: их создаёт ядро
  configEditor.ts        ┘
  model/                 данные: типы, конфиг, чистые преобразования
  ui/                    React-компоненты, кроме самого CustomChart
  hooks/                 React-хуки
  lib/                   чистые функции без React и без DOM
  engine/                мост к библиотеке отрисовки: единственное место с DOM вне хуков
```

### `index.ts` — единственная дверь наружу

Модуль объявляет свой публичный контракт одним файлом. Потребители импортируют **модуль
целиком**, а не его внутренние файлы:

```ts
import { CustomChart, DataAdaptor, SpecGenerator, ConfigEditor } from './modules/CustomChart';
import type { ChartConfig } from './modules/CustomChart';
```

Смысл не в удобстве записи, а в том, что раскладка `model`/`ui`/`hooks`/`lib` становится
внутренним делом модуля: файл переезжает из `model/` в `lib/` — правится один `index.ts`,
а не десяток импортов по проекту.

Реэкспортируется **граница, а не всё подряд**: контрактные единицы, дефолтный конфиг, типы его
формы, публичные хуки. Компоненты подложки из `ui/` и хелперы из `lib/` наружу не выводятся —
они внутренние, и вывод их через `index.ts` превращает контракт в оглавление.

Внутри модуля файлы импортируют друг друга **напрямую**, а не через свой же `index.ts`: путь
через границу собственного модуля — самоссылка, которая ничего не улучшает и легко замыкает
цикл.

### Корень — только точки входа

Кроме `index.ts` в корне лежит ровно то, что этот контракт отдаёт наружу: компонент и три
контрактные единицы, экземпляры которых создаёт ядро. Всё остальное живёт в подпапках.

Признак, что файл ошибочно оказался в корне: он не упомянут в `index.ts`.

### `model/` — данные и то, что их описывает

Типы конфига, дефолтный конфиг, чистые преобразования данных: `plugin.types.ts`,
`defaultConfig.json`, `getDefaultConfig.ts`, построение спеки из конфига и строк.

Признак `model/`: файл знает про **предметную область плагина** — полки, пилюли, конфиг,
строки — и ничего не знает про React и DOM.

### `ui/` — компоненты, кроме главного

Подложка целиком: шапка, оборот с описанием, оверлеи состояния (см. `chart-shell`). Каждый
компонент — функция от пропов, без обращений к DOM и без загрузки данных.

Признак `ui/`: возвращает JSX и не является `CustomChart`.

### `hooks/` — React-хуки

`useChartSize`, хук владения инстансом библиотеки отрисовки, хук подписки на события
(см. `chart-lifecycle`). Один хук — один файл, имя файла совпадает с именем хука.

Признак `hooks/`: имя начинается с `use` и внутри есть вызовы хуков React.

### `lib/` — чистые функции

Мелкие функции без React, без DOM и без знания о конфиге: чтение локализованного значения,
форматирование числа, разбор ключа строки.

Признак `lib/`: функция принимает примитивы или простые объекты и возвращает значение;
её тест не требует ни jsdom, ни моков.

### `engine/` — мост к библиотеке отрисовки

Адаптер движка и его типы: `engine/engine.ts` (реализация интерфейса `ChartEngine` —
`create`, `render`, `resize`, `destroy`) и `engine/engine.types.ts` (сам интерфейс и тип спеки).
Правила работы с ним — скилл `chart-lifecycle`, специфика ECharts — `echarts-engine`.

Папка заводится **вместе с подключением библиотеки отрисовки**; в шаблоне её нет, потому что
библиотека не выбрана. У неё особый статус: это единственное место модуля, где функция
принимает DOM-узел (`create(element: HTMLElement)`), — потому она и не `lib/`. Владение
инстансом при этом остаётся в `hooks/`: `engine/` только переводит вызовы, состояния не держит.

Признак `engine/`: файл упоминает библиотеку отрисовки по имени. Всё, что о ней не знает
(построение спеки из конфига и строк — `buildSpec`, перевод события в доменное — `toChartPoint`),
живёт в `model/` и тестируется без движка.

**Папки `utils/` в модуле нет и заводить её не нужно.** Две папки с близким смыслом
расходятся молча: через месяц никто не помнит, чем `utils` отличался от `lib`, и обе
превращаются в свалку. Всё, что тянет назваться утилитой, — это либо `lib/` (чистая функция),
либо `model/` (знает про конфиг).

## Граница между `model/` и `lib/`

Единственное место, где раскладка вызывает споры. Проверка — по знанию о предметной области:

| Функция                              | Куда     | Почему                                         |
| ------------------------------------ | -------- | ---------------------------------------------- |
| `buildSpec(config, plotData, theme)` | `model/` | читает конфиг и строки плагина                 |
| `getDatasetId(config)`               | `model/` | знает про полки и пилюли                       |
| `getLocal(source, key, locale)`      | `lib/`   | работает с любым объектом, про конфиг не знает |
| `formatNumber(value, precision)`     | `lib/`   | числа и есть числа                             |

Если сомневаешься — `model/`. Ошибка «положил в model то, что могло бы жить в lib» безвредна;
обратная — превращает `lib/` в место, куда постепенно переезжает вся логика.

## Спеки

Спек лежит **рядом со своим файлом**, в той же папке: `model/getDefaultConfig.spec.ts`,
`hooks/useChartSize.spec.tsx`. Отдельного каталога тестов в проекте нет, и заводить его не
нужно — при переносе файла спек едет вместе с ним одной командой.

## Импорты

Все импорты относительные, алиасов в проекте нет. После раскладки пути становятся длиннее —
это нормально и полезно: `../model/plugin.types` сразу говорит, что импортируется тип
предметной области, а не хелпер.

`index.ts` есть **только у модуля** — у подпапок его быть не должно. `model/index.ts`,
реэкспортирующий всё содержимое папки, прячет настоящее место объявления и делает циклические
импорты незаметными; внутри модуля файлы адресуются прямыми путями.

**Когда прямой путь обязателен и снаружи.** Если потребитель находится в цикле с модулем —
модуль зависит от него, а он от модуля, — импорт через `index.ts` замкнёт цикл. Так устроен
`ComponentTypeManager`: `CustomChart` его использует, поэтому сам менеджер импортирует
`dataAdaptor.ts` и остальные напрямую, а не через границу модуля. Такой импорт снабжается
комментарием с причиной, иначе следующий «исправит» его обратно.

Цикл в ES-модулях не всегда падает сразу: пока обращения отложены до вызова функций, всё
работает, а ломается позже — при первом обращении на верхнем уровне модуля, в коде, который
цикла не создавал.

## Когда заводить новый файл

Правило второго потребителя: функция, нужная **одному** файлу, живёт в этом файле; переезжает
в `lib/` или `model/`, когда у неё появляется второй потребитель. Файл на одну функцию,
которую зовут из одного места, — это лишний уровень навигации, а не структура.

Исключение — чистые функции, вокруг которых строится тест: их выносят сразу, потому что
тестировать функцию проще, чем компонент, который её содержит.

## Частые ошибки

| Ошибка                                                      | Чем плоха                                                                                |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `utils/` рядом с `lib/`                                     | граница между ними не удерживается; обе становятся свалкой                               |
| Вспомогательный компонент в корне модуля                    | корень перестаёт отвечать на вопрос «что здесь точки входа»                              |
| Типы, объявленные в файле компонента                        | тип нужен адаптору и спеке — его место в `model/plugin.types.ts`                         |
| Хук, объявленный внутри файла компонента                    | не тестируется отдельно; в `hooks/` он проверяется без рендера компонента                |
| Обращение к DOM в файле из `model/` или `lib/`              | сломана граница чистого кода: тест такой функции требует jsdom                           |
| Адаптер движка в корне модуля или в `lib/`                  | корень — только точки входа, `lib/` — без DOM; место адаптера `engine/`                  |
| Имя библиотеки отрисовки упомянуто вне `engine/`            | замена движка перестаёт быть заменой одной папки                                         |
| `index.ts` у подпапки (`model/index.ts`)                    | скрывает место объявления, маскирует циклические импорты                                 |
| Импорт внутренностей модуля в обход `index.ts`              | раскладка перестаёт быть внутренним делом: переезд файла правит импорты по всему проекту |
| Импорт через `index.ts` из кода, от которого зависит модуль | замыкает цикл; нужен прямой путь с комментарием о причине                                |
| Хелпер из `lib/` выведен в `index.ts`                       | контракт превращается в оглавление модуля                                                |
| Спек в отдельном каталоге                                   | расходится с кодом при первом же переносе файла                                          |

## Смежные скиллы

Раскладка отвечает на вопрос «куда положить», а не «что написать»:

- `data-query-contract` — запрос к бэкенду и разбор ответа (`dataAdaptor.ts`, `model/`);
- `chart-lifecycle` — инстанс библиотеки отрисовки, эффекты, события (`hooks/`, `engine/`);
- `echarts-engine` — реализация адаптера на ECharts (`engine/`);
- `chart-shell` — подложка вокруг холста (`ui/`);
- `typescript-coding-standards` — именование, типизация, порядок импортов внутри файла.
