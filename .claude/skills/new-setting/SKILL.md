# Новая настройка панели редактора

Настройка живёт в пяти местах сразу. Пропуск любого — тихий отказ: ни ошибки компиляции, ни предупреждения в консоли, настройка просто не работает. Исключение одно, и его видно в таблице: пятую точку (дефолт) можно опустить, когда настройка при рендере не читается.

## Точки

| #   | Что                                                                                  | Где                                                      |
| --- | ------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 1   | Контрол внутри секции, зовёт `changeChart(command, { value })` — ровно два аргумента | `src/modules/CustomSettings/sections/<Секция>.tsx`       |
| 2   | Секция подключена в панели                                                           | `src/modules/CustomSettings/Settings.tsx`                |
| 3   | Запись `command → путь в конфиге` в таблице команд                                   | `src/modules/CustomReducers/changeCustomChartReducer.ts` |
| 4   | Поле в типе конфига                                                                  | `src/modules/CustomChart/model/plugin.types.ts`          |
| 5   | Поле дефолта (если настройка читается при рендере)                                   | `src/modules/CustomChart/model/defaultConfig.json`       |

**Шестая точка появляется, когда поле корневое и его может не оказаться в отчёте, сохранённом прошлой версией плагина.** Такое поле читается **только** через общий хелпер `readConfigField` — заводится он в `src/modules/CustomChart/model/configFields.ts` вместе с первым таким полем, там же объявляется тип `OptionalConfigField` с перечнем этих полей. Внутри хелпера — `??`, а не `||`: `0` и `false` бывают валидными значениями настройки. Дефолт при этом всё равно живёт в `defaultConfig.json`, `readConfigField` берёт его оттуда; второго источника у дефолта нет.

Правило именно про **корневые** поля: вложенная ветка (`legend.show`) читается с опциональной цепочкой и своим дефолтом по месту — отдельного хелпера ей не нужно.

**Отдельного компонента на каждый пункт в этом плагине нет.** Пункт — это UI-примитив ядра (`SettingsItem` и контрол внутри) прямо в теле секции; каталогов вида `<Что><Контрол>SettingItem/` быть не должно. Компонент заводится, только когда пункт несёт собственное состояние или заметную логику, — как общие `SelectSettingItem` и `NumberSettingItem` ниже.

Секции — файлы в `src/modules/CustomSettings/sections/`. Сейчас в шаблоне их нет ни одной — `Settings.tsx` рендерит `null`. Первая секция заводится с нуля по описанному ниже шаблону и подключается в `Settings.tsx`; порядок вывода там же задаёт порядок в панели, вперемешку с готовыми секциями ядра из `pluginImports.sections`. Вместе с первой секцией заводятся два общих файла панели:

- `src/modules/CustomSettings/types.ts` — `ChangeChart` и тип props секции (`SettingsSectionProps`); дальше типы берутся отсюда, а не копируются в файл секции;
- `src/modules/CustomSettings/sectionConfig.ts` — `getSectionConfig(component)`, единственное место, где написан порядок `configDraft || config || {}`. Это **контракт панели, снятый на портале**: во время правки настроек актуален черновик, у только что созданного компонента черновика ещё нет, а до первого рендера может не быть и конфига. Своё выражение `configDraft || config` по месту — верный способ забыть одно из трёх звеньев в четвёртой секции из шести.

## Порядок работы

1. **Уточни у пользователя**, чего не хватает в формулировке: имя настройки в интерфейсе (русский литерал прямо в JSX), секция (новая или существующая), тип контрола, поле в `config`, значение по умолчанию.
2. **Возьми шаблон контрола** из раздела «Шаблоны контролов» — источник истины по оформлению пункта именно он, а не соседний файл. Сосед показывает, куда пункт встаёт и как читается конфиг; разошёлся с шаблоном — прав шаблон, а соседа стоит привести к нему заодно.
3. **Реализуй через цикл `/tdd`**: `test-writer` пишет красный тест на `changeCustomChartReducer` и, если меняется или заводится секция, на неё саму; `implementer` доводит до зелёного.

   Первая настройка отдельно: действующий `changeCustomChartReducer.spec.ts` фиксирует поведение заглушки (`next` — тот же объект, `autoApplySettings` не вызван). С появлением таблицы `COMMANDS` эти утверждения становятся ложными. Переписывает их **`test-writer` в фазе RED** — это его файл; `implementer` спек не трогает и, упёршись в него, возвращает вопрос. Редьюсер — чистая функция, тестируется без окружения; секция — с docblock'ом `/** @jest-environment jsdom */` и заглушками UI-примитивов ядра.

4. Прогони `npm test` и `npm run lint`. Типы гонял PostToolUse-хук после каждой правки, но для `*.spec.*` он намеренно не блокирующий — если правился только спек, прогони `npm run typecheck` отдельно.
5. Отдай на проверку сабагенту `settings-flow-reviewer` — он сверяет замыкание команд и вызов `autoApplySettings`.

## Шаблоны контролов

UI-примитивы **не импортируются** — приходят из ядра через `pluginImports.components` в `Settings.tsx`, а секции получают уже сужённый набор пропом. Значение читается через `getSectionConfig(component)` (`configDraft` с фолбэком на `config`), обработчик зовёт `changeChart` напрямую.

Контрол выбирается по типу значения, а не по вкусу. Шаблон каждого — ниже, дословно; отклоняться от него можно, только когда у пункта есть собственное состояние или логика, которых в шаблоне нет.

| Значение настройки         | Контрол               | Шаблон                                  |
| -------------------------- | --------------------- | --------------------------------------- |
| Булево (вкл/выкл)          | `SettingsToggle`      | «Булева настройка» ниже                 |
| Цвет                       | `SettingsColorPicker` | «Цвет» ниже                             |
| Число                      | `NumberSettingItem`   | «Числовые настройки» следующим разделом |
| Одиночный выбор из списка  | `SelectSettingItem`   | «Одиночный выбор» ниже                  |
| Набор значений (0..N штук) | `SettingsCheckbox`    | по одному пункту на элемент набора      |

### Булева настройка

**Тумблер, `SettingsItem` с `type='inline'`, у тумблера — ни `label`, ни своего заголовка.** Условный пример — «Показывать легенду», пишущий поле `legend.visible`:

```tsx
<SettingsItem
  type='inline'
  title='Показывать легенду'
>
  <SettingsToggle
    toggled={Boolean(legend.visible)}
    onToggle={(_event: unknown, checked: boolean) => changeChart('TOGGLE_LEGEND', { value: checked })}
  />
</SettingsItem>
```

Почему так, а не иначе:

| Элемент шаблона            | Причина                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `type='inline'`            | подпись и тумблер в одну строку — так выглядят штатные пункты ядра; без него пункт встаёт в две строки |
| Заголовок в `SettingsItem` | заголовок пункта задаёт контейнер, и ровно один раз                                                    |
| Нет `label` у тумблера     | подпись вида «Вкл»/«Выкл» дублирует и заголовок, и само положение тумблера                             |
| Тумблер, а не чекбокс      | чекбокс — для набора, где отмечают несколько элементов; одиночное «да/нет» ядро показывает тумблером   |

**Props именно такие: `toggled` и `onToggle`, а не `checked`/`onChange`.** Проверено по `propTypes` компонента в бандле ядра (`displayName="SettingsToggle"`): он принимает `toggled`, `onToggle`, `label`, `labelPosition`, `labelSize`, `disabled`, `title`, `style` — и сам прокидывает их в MUI-свитч как `checked`/`onChange`. Передашь `checked` — тумблер отрисуется всегда выключенным и команду не отправит, молча. **Новое значение приходит вторым аргументом** обработчика, первым идёт событие.

Читай значение так, чтобы `false` и `0` оставались валидными настройками — не заменяй `Boolean(config.legend?.visible)` на `config.legend?.visible || true`: `||` подменит `false` дефолтом. Для корневых полей, которых может не быть в старом отчёте, это уже решено — `readConfigField` использует `??`.

### Цвет

```tsx
<SettingsItem
  type='inline'
  title='Цвет шрифта'
>
  <SettingsColorPicker
    color={tooltip.fontColor ?? null}
    float='right'
    onChange={(value: string | undefined) => changeChart('SET_TOOLTIP_FONT_COLOR', { value: value ?? null })}
  />
</SettingsItem>
```

| Элемент шаблона           | Причина                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |
| `float='right'`           | пипетка прижимается к правому краю пункта, как у штатных цветовых пунктов ядра                         |
| `color={... ?? null}`     | «цвет не задан» — это `null`, а не `undefined`: `??` не съедает пустую строку и не путает со сбросом   |
| `value ?? null` в команде | сброс цвета приходит как `undefined`, а в конфиге обязан лежать `null` — иначе поле исчезнет из отчёта |

### Одиночный выбор

Пункт не собирается заново в каждой секции — для него заводится общий `src/modules/CustomSettings/SelectSettingItem.tsx`, он же держит контракт `SettingsMultiselect` ядра (`multiple: false`, `clearable: false`, пустой `title` у самого мультиселекта). Список значений задаётся константой модуля секции:

```tsx
const TEMPLATE_OPTIONS: SelectOption[] = [
  { value: 'name', name: 'Название категории' },
  { value: 'value', name: 'Значение' },
  { value: 'nameValue', name: 'Название + значение' },
];

<SelectSettingItem
  title='Шаблон'
  options={TEMPLATE_OPTIONS}
  value={dataLabels.template ?? 'nameValue'}
  components={{ SettingsItem, SettingsMultiselect }}
  onChange={(value) => changeChart('SET_LABEL_TEMPLATE', { value })}
/>;
```

**Настройка «шаблон» — всегда список предустановленных вариантов, а не текстовое поле.** Свободный ввод шаблона означает свой мини-язык подстановок, его разбор и молчаливую поломку отчёта при опечатке; готовый список закрывает те же случаи и проверяется тестом на каждую опцию.

Секция целиком получает объект props вида `{ component, changeChart, components }` — тип `SettingsSectionProps` заводится в `src/modules/CustomSettings/types.ts` вместе с первой секцией (см. «Точки» выше) и дальше импортируется оттуда, а не копируется в файл (форма — в TS-конвенциях, скилл `typescript-coding-standards`). Набор нужных примитивов каждая секция сужает под себя своим локальным интерфейсом `UIComponents`. У каждой секции есть `displayName`.

## Числовые настройки: поле, а не слайдер

**Слайдер для числа не использовать** — ни для размера шрифта, ни для толщины линии, ни для
отступов и прочих величин, у которых есть точное осмысленное значение. Слайдером нельзя
поставить ровно `12`: пользователь целится мышью, промахивается, а на каждое движение ползунка
уходит команда в редьюсер. Слайдер уместен там, где значение выбирается на глаз и точность не
важна, — прозрачность, например.

Числовой пункт не собирается заново в каждой секции — для него заводится общий
`src/modules/CustomSettings/NumberSettingItem.tsx`, повторяющий одноимённый штатный пункт ядра:

```tsx
<NumberSettingItem
  title='Размер шрифта'
  value={typeof dataLabels.fontSize === 'number' ? dataLabels.fontSize : 12}
  min={8}
  max={32}
  components={{ SettingsItem, SettingsTextField }}
  onChange={(value) => changeChart('SET_LABEL_FONT_SIZE', { value })}
/>
```

Внутри он — `SettingsItem` с `type='inline'` и `SettingsTextField` с `numeric`, `min`, `max`,
`step` и классом ядра `NumberSettingItem__input`.

Что обязательно на стороне секции:

| Элемент             | Зачем                                                                      |
| ------------------- | -------------------------------------------------------------------------- |
| `min`, `max`        | границы осмысленного диапазона; без них в конфиг уезжает `0` или `999`     |
| Имя команды         | `UPPER_SNAKE_CASE` — то же имя, что ключ в таблице `COMMANDS` редьюсера    |
| Значение с дефолтом | в отчёте, сохранённом до появления настройки, поля нет — дефолт обязателен |
| `step`              | только если шаг не единица: по умолчанию пункт целочисленный               |

**Ширину поля задаёт CSS портала.** Класс `NumberSettingItem__input` объявлен в таблице стилей
ядра (`width: 60px`) и используется его собственным числовым пунктом — брать его, а не заводить
свой класс и свой `settings.scss`. Проверяется одной командой:

```bash
grep -ho "NumberSettingItem__input[^{]*{[^}]*}" prebuild/*.css
```

Своей таблицы стилей у шаблона нет вовсе, и заводить её ради числового поля не нужно. Отступы,
шрифт и выравнивание приходят из CSS портала через `SettingsItem`. Пайплайн `.scss` при этом
собран (`sass-loader` → `css-loader` → `style-loader`) — файл стилей заводится только вместе с
настройкой, которой действительно нужен собственный стиль.

**Приведение к числу живёт в `NumberSettingItem`, а не в редьюсере**: в конфиге обязано лежать
число, иначе сравнение и арифметика на стороне отрисовки поедут молча. Промежуточный ввод
(`-`, `.`, пустое поле) даёт `NaN` — такое значение пункт не отправляет вовсе.

Три факта про `SettingsTextField numeric`, снятые с бандла ядра, — без них тест на пункт
пишется неправильно:

| Факт                                                                                | Что из этого следует                                                                         |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Значение приходит **вторым** аргументом: `onChange(event, value)`                   | обработчик читает второй аргумент, а не первый                                               |
| В режиме `numeric` поле само делает `parseFloat(Number(value \|\| '0').toFixed(5))` | наружу уходит **число**, а не строка; хелпер страхует от промежуточных `'-'` и `'.'`         |
| `onChange` вызывается через `setTimeout(..., 500)` — поле дебаунсит само            | компонентный спек на поле нуждается в фейковых таймерах или `findBy*`; свой дебаунс не нужен |

## Шаблон записи в редьюсере

Устройство редьюсера целиком — скилл `custom-reducers-module`: почему таблица вместо ветвлений,
почему копия черновика, что в редьюсер не кладут. Здесь — только то, что делает новая настройка.

`changeCustomChartReducer.ts` сейчас — заглушка (`(state, action, options) => state`), с рабочей версией в комментарии файла. Заводя первую настройку, замени тело на таблицу соответствия `COMMANDS` — веток `if (action.command === ...)` в редьюсере быть не должно:

```ts
/**
 * Таблица «команда → путь в конфиге». Веток `if` на команды в этом файле быть не должно:
 * новая настройка добавляется строкой сюда и пунктом в секции панели настроек.
 *
 * Вложенные поля конфига пишутся через точку: `'outline.width'`.
 */
export const COMMANDS: Record<string, string> = {
  TOGGLE_LEGEND: 'legend.visible',
  // сюда — новая настройка
};

/** Пишет значение по пути с точками, создавая недостающие объекты. */
const setByPath = (target: Record<string, unknown>, path: string, value: unknown): void => {
  const keys = path.split('.');
  const last = keys.pop() as string;
  const parent = keys.reduce<Record<string, unknown>>((node, key) => {
    if (typeof node[key] !== 'object' || node[key] === null) node[key] = {};
    return node[key] as Record<string, unknown>;
  }, target);
  parent[last] = value;
};

export default function changeCustomChartReducer(
  state: PluginState,
  action: PluginAction,
  options: CustomReducersOptions,
): PluginState {
  const path = COMMANDS[action?.command];
  if (!path) return state;

  const configDraft = structuredClone(state.component.configDraft);
  setByPath(configDraft, path, action?.settings?.value);

  const nextState = {
    ...state,
    component: { ...state.component, configDraft },
  };

  return options.autoApplySettings(nextState);
}
```

Редьюсер клонирует конфиг (`structuredClone`) и пишет по пути, создавая недостающие подобъекты, — поэтому подобъект, которого нет в старом отчёте, руками создавать не нужно.

**Готовая секция ядра команду не заводит.** Секции из `pluginImports.sections` (`precisionSliderContent`, `suffixSelectContent`, `DataOptionsContent`, `titleTextFieldContent`…) пишут своё поле в `component.configDraft` собственными колбэками — **в обход `changeChart` и таблицы `COMMANDS`**; установлено проверкой на портале. Заводить им запись в таблице не нужно и вредно: она никогда не сработает, а следующий читатель решит, что настройка проходит через редьюсер. Пять точек этого скилла — про **свой** пункт панели; подключение готовой секции сводится к одной строке в `Settings.tsx` плюс полю в `ChartConfig`.

**Дефолт в `defaultConfig.json` добавляй всегда.** Оговорка «если настройка читается при рендере» в таблице точек описывает единственное исключение — значение, которое не читает ни секция, ни компонент, а такого у настройки панели практически не бывает: секция обязана что-то показать до первой правки. Сомневаешься — добавляй; лишний дефолт безвреден, отсутствующий даёт пустой контрол в новом отчёте.

Рантайм-зависимостей у шаблона нет вовсе. Если предпочитаешь `lodash.set` вместо `setByPath`, пакет придётся добавить — и он попадёт в бандл.

Новую настройку нужно объявить в `ChartConfig` (`src/modules/CustomChart/model/plugin.types.ts`) — отдельного типа черновика в проекте нет, `configDraft` типизируется тем же интерфейсом.

Если значение настройки нуждается в приведении типа (например строка из текстового поля должна лечь в конфиг числом или `null`) — таблица `COMMANDS` кладёт значение как есть, приведение нужно добавить в редьюсер до записи по пути или обсудить с пользователем отдельный путь для таких команд.

## Обязательное: autoApplySettings

Возврат редьюсера обязан быть обёрнут в `options.autoApplySettings(state)`. Это **функция ядра, а не флаг**: без неё правка осядет в `configDraft` и не доедет до компонента. Она же учитывает режим ручного применения, помечая черновик как dirty.

Заводя первую настройку — добавь обёртку сам (см. пример выше) и не добавляй путей выхода в обход неё.

## Частые ошибки

| Симптом                                             | Причина                                                                                              |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Настройка меняется в панели, диаграмма не реагирует | Команды нет в таблице `COMMANDS`, либо имя разъехалось между вызовом `changeChart` и ключом таблицы  |
| Правка применяется, но откатывается                 | Обход `autoApplySettings`                                                                            |
| Переключатель не выключается                        | Значение читается через `\|\|` вместо явной проверки — `false` подменяется дефолтом                  |
| Секция показывает `undefined`                       | Секция читает один путь, таблица пишет другой                                                        |
