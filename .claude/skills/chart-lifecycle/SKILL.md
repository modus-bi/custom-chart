# Жизненный цикл холста

## Суть

Библиотека отрисовки — единственное императивное место в плагине: она владеет DOM-узлом, держит
инстанс, подписки и таймеры. Задача не в том, чтобы «написать интеграцию», а в том, чтобы
**сжать императив до минимума и держать его на границе**: всё вычисление — чистыми функциями,
всё владение — в одном эффекте с обязательным `cleanup`.

Скилл нейтрален к движку: ECharts, D3, Chart.js, canvas руками. Шаблон библиотеку отрисовки
не выбирает, и правила ниже от неё не зависят.

Что рисуется вокруг холста (шапка, оборот, оверлеи) — скилл `chart-shell`. Откуда берутся
строки — `data-query-contract`. Специфика ECharts — `echarts-engine`.

## Разделение, из которого всё следует

```
config + plotData ──► buildSpec()          чистая функция, тестируется без DOM
                          │
                          ▼
                    useChartSpec()          useMemo: пересчёт только при смене входов
                          │
                          ▼
                    useChartRender()        эффект: единственное место, где спека
                          │                 попадает в движок
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
useChartInstance()   useChartSize()   useChartEvents()
создание/уничтожение   размер          подписки, снятые в cleanup
```

Правило, которое проверяется чтением диффа: **в файле с `buildSpec` не должно быть ни одного
обращения к DOM или к инстансу, а в файле с эффектами — ни одной ветки бизнес-логики.** Если
эффект начинает решать, какой должна быть спека, — это ошибка разделения, а не стиль.

## Что делает каждая фаза

| Фаза        | Когда                                 | Чем нельзя обойтись                                     |
| ----------- | ------------------------------------- | ------------------------------------------------------- |
| Создание    | один раз, на непустой узел контейнера | пересоздавать инстанс на каждый рендер                  |
| Обновление  | при смене спеки                       | пересоздавать инстанс вместо обновления                 |
| Размер      | при смене размеров контейнера         | слушать `resize` окна: плитку тянут без ресайза окна    |
| События     | один раз на инстанс                   | подписываться внутри обновления — обработчики накопятся |
| Уничтожение | при размонтировании и при смене узла  | «оно само»: инстанс держит DOM, таймеры и слушателей    |

## Адаптер движка

Нейтральность держится на одном узком интерфейсе. Движок подключается через объект с четырьмя
функциями — не класс, не наследование:

```ts
/** Мост к библиотеке отрисовки. Всё, что знает о ней остальной код. */
export interface ChartEngine<TSpec, TInstance> {
  create: (element: HTMLElement) => TInstance;
  render: (instance: TInstance, spec: TSpec) => void;
  resize: (instance: TInstance, size: ChartSize) => void;
  destroy: (instance: TInstance) => void;
}
```

Раскладка задана скиллом `custom-chart-module`: интерфейс — `engine/engine.types.ts`,
реализация — `engine/engine.ts`, оба внутри `src/modules/CustomChart/`. Это единственная папка
модуля, которой разрешено знать имя библиотеки отрисовки и принимать DOM-узел; в корень модуля
и в `lib/` адаптер не кладётся. Замена библиотеки — замена этой папки, остальной код не
трогается. Тесты подставляют фиктивный движок и проверяют **порядок вызовов**, не рисуя ничего.

Чистые функции вокруг движка — `buildSpec` и `toChartPoint` — про библиотеку не знают и живут
в `model/`, хуки владения — в `hooks/`.

## Хуки

Инстанс живёт в `ref`, а не в состоянии: его смена не должна вызывать рендер, а `useState`
вызвал бы. Это единственное отступление от «всё через состояние», и оно вынужденное.

```ts
/**
 * Создаёт инстанс на узле и уничтожает его при размонтировании или смене узла.
 * Возвращает вместе с ссылкой номер поколения: он меняется на каждое пересоздание.
 */
export function useChartInstance<TSpec, TInstance>(
  engine: ChartEngine<TSpec, TInstance>,
  ref: RefObject<HTMLElement | null>,
  size: ChartSize,
): [RefObject<TInstance | null>, number] {
  const instanceRef = useRef<TInstance | null>(null);
  const [generation, setGeneration] = useState(0);

  useEffect(() => {
    const element = ref.current;
    // Нулевой размер — узел ещё не разложен: часть библиотек на нём ругается в консоль
    // и рисует пустоту, а пересоздавать инстанс потом дороже, чем подождать кадр.
    if (!element || !size.width || !size.height) return undefined;

    instanceRef.current = engine.create(element);
    setGeneration((value) => value + 1);

    return () => {
      if (instanceRef.current) {
        engine.destroy(instanceRef.current);
        instanceRef.current = null;
      }
    };
  }, [engine, ref, size.width === 0, size.height === 0]);

  return [instanceRef, generation];
}
```

**Зачем номер поколения.** `instanceRef` — объект `useRef`, между рендерами он один и тот же. Значит эффект отрисовки с зависимостями `[engine, instanceRef, spec]` не перезапустится при пересоздании инстанса: спека прежняя, ссылка прежняя, а инстанс уже новый и пустой. На первом монтировании это не проявляется — эффекты идут в порядке объявления, и `create` успевает раньше `render`, — поэтому дефект тихий и вылезает позже, при смене узла или движка. Номер поколения в зависимостях эффектов отрисовки, размера и подписок закрывает дыру.

Спека — чистое вычисление, поэтому `useMemo`, а не эффект и не состояние:

```ts
const spec = useMemo(() => buildSpec(config, plotData, theme), [config, plotData, theme]);
```

Отрисовка — один эффект, зависящий от спеки. Он ничего не решает: получил спеку — отдал движку.

```ts
useEffect(() => {
  const instance = instanceRef.current;
  if (!instance) return;
  engine.render(instance, spec);
}, [engine, instanceRef, spec, generation]);
```

Размер приходит из `useChartSize` (`src/modules/CustomChart/hooks/useChartSize.ts`) — он уже собран на
`ResizeObserver`, то есть ловит перетаскивание границ плитки, а не только ресайз окна:

```ts
const { width, height } = useChartSize(containerRef);

useEffect(() => {
  const instance = instanceRef.current;
  if (!instance || !width || !height) return;
  engine.resize(instance, { width, height });
}, [engine, instanceRef, width, height, generation]);
```

Нулевой размер пропускается намеренно: пока плитка не отрисована, `ResizeObserver` отдаёт `0` —
`resize` на нулевом контейнере часть библиотек воспринимает как «схлопнуться».

**Про `engine` в зависимостях:** объект движка должен быть стабильным — константа модуля или
`useMemo`. Литерал, собранный в теле компонента, на каждом рендере новый и будет пересоздавать
инстанс. Это тот случай, когда функциональный стиль наказывает за небрежность молча.

**Ссылки от ядра стабильными не бывают.** Инжекты (`loadDatas`, `reloadDatas`), `hsTheme`,
`reportOptions` и всё, что из них вычисляется (палитра, набор цветов), ядро вправе отдавать
новым объектом на каждый рендер родителя. Положил такое в зависимости эффекта по ссылке —
получил обновление на каждый чужой ре-рендер: диаграмма перерисовывается вхолостую, а таймеры
и подписки пересоздаются, не дожив до срабатывания. Лечится по роду значения: **массив или
объект сравнивается по содержимому**, инжекты берутся внутри эффекта из `ref`, а в зависимостях
остаются примитивы.

**Вне статуса «готово» инстанс освобождается.** Диаграмма скрыта сообщением «нет данных», а
инстанс жив — под сообщением останется устаревшая картинка, и она всплывёт, как только статус
вернётся в `ready`. Уничтожение — то же самое `destroy`/`dispose`, что и в `cleanup`; узел
контейнера при этом не трогается. Перечень статусов и кто их считает — скилл `chart-shell`.

**Классовый компонент — допустимая форма владельца инстанса.** Инстанс живёт вне рендер-цикла,
и фазы `componentDidMount` → `componentDidUpdate` → `componentWillUnmount` иногда читаются
прямее, чем те же фазы, размазанные по эффектам с `ref`. Тогда порядок внутри
`componentDidUpdate` важен и пишется явно: сначала `resize()` под новый размер, потом пересборка
спеки — геометрия, посчитанная в абсолютных пикселях, сама под `resize()` не подстраивается.
Это выбор, а не обязанность: хуки выше остаются штатной формой, а `UNSAFE_`-методы не нужны ни
в одной из них.

## События и интерактив

Обработчики подписываются **один раз на инстанс**, а не при каждом обновлении спеки. Разделение
то же: чистая функция переводит событие движка в доменное, эффект только раздаёт его инжектам
ядра.

```ts
/** Событие движка → доменное. Чистая: ни инжектов, ни DOM. */
export const toChartPoint = (event: EngineEvent, config: ChartConfig): ChartPoint | null => { … };
```

Инжекты ядра, которые принимает `CustomChart`. **В контракте их нет**: `chartPlugin.d.ts`
объявляет props компонента как `PluginInjectedProps = any` и набор инжектов не раскрывает.
Сверять по `docs/api` (перечень props и инжектов) и по бандлу ядра в `prebuild/app.*.js` —
грепом, а не по памяти:

| Инжект                                    | Сигнатура и смысл                                                                  |
| ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `drillDown`                               | `(componentId, categoryFieldName, categoryValue)` — только когда `drillDownActive` |
| `setCursorClicked`                        | `({ containerID, chartID, category: { name, field }, value: { amount, field } })`  |
| `setCursorHovered`                        | то же; при уходе курсора — `{ chartID, category: null, value: null }`              |
| `changeFilterCategories`                  | режим фильтрации: выбранные категории компонента                                   |
| `changeMultipleGlobalFilterValueAndApply` | режим фильтрации: применение к глобальным фильтрам отчёта                          |
| `reloadDatas`                             | та же сигнатура, что `loadDatas`; для интервального обновления по `config.refresh` |

Развилка клика в штатных компонентах одна и та же, и порядок проверок в ней неочевидный:

1. Настроена иерархия детализации (`config.drill.hierarchy` не пуст) — режим фильтрации
   **выключен принудительно**, независимо от `config.filterMode`.
2. Иначе `config.filterMode` включён — клик фильтрует.
3. Иначе клик уводит в drill-down, и только если ядро передало `drillDownActive`.

Курсор (`setCursorClicked`) выставляется во всех случаях. `Ctrl` при клике в режиме
фильтрации добавляет категорию к выбранным, а не заменяет выбор.

Курсор — межкомпонентный: ядро рассылает его событием `dataCursorChanged` на `window`, и по
нему штатные компоненты подсвечивают свою точку. Плагину эта подписка нужна, только если он
хочет отвечать на курсор соседей; снимать её в `cleanup` обязательно.

## Чего не делать

Перечень не умозрительный: каждая строка — ошибка, которая встречается в существующих
интеграциях и стоит либо утечки, либо многократного срабатывания обработчика.

| Антипаттерн                                                       | Чем оборачивается                                                                                                                                          |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Размонтирование без уничтожения инстанса                          | инстанс и его DOM переживают компонент; переоткрытие отчёта копит их                                                                                       |
| Глобальный реестр инстансов (`window.charts[id] = …`) без очистки | ссылка держится вечно — сборщик мусора бессилен. Ядро такой реестр ведёт, но чистит его при размонтировании: копируя приём из бандла, копируй обе половины |
| Подписка на события внутри обновления спеки                       | обработчики накапливаются: один клик срабатывает столько раз, сколько было обновлений                                                                      |
| Слушатель `resize` на окне вместо наблюдения за контейнером       | не ловит перетаскивание границ плитки — самый частый сценарий смены размера                                                                                |
| Таймеры и `requestAnimationFrame` без снятия в `cleanup`          | колбэк стреляет по уже уничтоженному инстансу                                                                                                              |
| Рисование в фазе рендера (в теле компонента, до эффекта)          | побочный эффект там, где React вправе повторить или отменить рендер                                                                                        |
| Глубокое сравнение всего конфига на каждый рендер                 | цена сравнения превышает цену перерисовки; ссылочных зависимостей эффекта достаточно                                                                       |
| Рендер React внутрь узла, которым владеет движок                  | два владельца у одного DOM-узла; состояния рисуются в подложке — см. `chart-shell`                                                                         |
| Пересоздание инстанса вместо обновления спеки                     | сбрасывается пользовательское состояние: выключенные серии, зум, выделение                                                                                 |
| Пересоздание узла контейнера при смене статуса                    | движок теряет свой DOM; прятать через `visibility: hidden`, никогда `display: none`                                                                        |

Отдельно про форму компонента: всё перечисленное типично для классовых компонентов с
`UNSAFE_`-методами, где фазы жизненного цикла размазаны по `componentWillReceiveProps`,
`shouldComponentUpdate` и `componentWillUpdate`. `CustomChart` функциональный, и каждая фаза
выражается своим эффектом с явным `cleanup` — переносить классовую форму в шаблон не нужно.

## Конкретные движки

Скилл нейтрален намеренно: шаблон библиотеку отрисовки не выбирает. Специфика конкретного
движка — как импортировать, что умеет его метод обновления, как устроены события — живёт
отдельно.

Для ECharts — скилл `echarts-engine`: развилка «библиотека портала или своя» и изоляция от
глобальной, режимы `setOption`, подписки через `on`/`off`, перенос исходной строки в точку
данных, выбор рендерера.

Для другого движка отдельного скилла пока нет: реализуй `ChartEngine` по его документации,
а правила этого скилла — про фазы, эффекты и cleanup — остаются теми же.

## Тестирование

Функциональное разделение окупается именно здесь.

- `buildSpec(config, plotData, theme)` — чистая функция, тестируется в окружении `node`
  без DOM и без движка. Это основная масса тестов: состав серий, оси, форматирование,
  поведение на пустых данных.
- `toChartPoint(event, config)` — так же чисто: клик по точке превращается в доменный объект.
- Хуки — компонентный спек с docblock'ом `/** @jest-environment jsdom */` и **фиктивным
  движком**: `{ create: jest.fn(() => instance), render: jest.fn(), resize: jest.fn(),
destroy: jest.fn() }`. Проверяется порядок: `create` один раз; `render` при смене спеки и
  не чаще; `resize` при смене размера; `destroy` при размонтировании ровно один раз.
  `ResizeObserver` в jsdom отсутствует — подменяется заглушкой в спеке.

Цикл — `tdd`: спеки пишет `test-writer`, реализацию `implementer`.

Тест на утечку стоит написать сразу, он дешёвый: смонтировать, размонтировать, проверить, что
`destroy` вызван и что после размонтирования ни один обработчик не срабатывает. Именно эта
проверка ловит то, чем болеет референс.

## Проверка в портале

Тесты не покажут ни одной из настоящих проблем интеграции — их видно только в отчёте:
перетащить границу плитки (диаграмма перерисовывается без обрезки), свернуть и развернуть
панель, переключить вкладку отчёта и вернуться (инстанс не задвоился), кликнуть по точке в
обычном режиме и в режиме фильтрации, проверить drill-down и возврат, открыть отчёт дважды
подряд и посмотреть в DevTools, что число узлов холста не растёт.
