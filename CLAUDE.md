# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Шаблон плагина для BI-платформы **ModusBI**. Собирается webpack'ом в единый UMD-бандл `build/custom_chart_0.js` (library `CustomChart0`), который загружается ядром платформы. В `externals` только `react` и `react-dom` — их предоставляет ядро. Библиотеку отрисовки шаблон не выбирает: `CustomChart` рендерит пустой контейнер вместо диаграммы (подробности — в разделе «Поток данных», предупреждение про выбор библиотеки — в «Соглашениях»). Панель настроек и редьюсер команд — тоже заглушки: своих настроек у шаблона нет.

## Источник истины по контракту с ядром

**`prebuild/api/chartPlugin.d.ts`** — формальный контракт: обязательные экспорты, сигнатуры методов, что ядро фактически передаёт в каждый. Рядом `README.md` (пояснения) и `version.json` (сейчас `contractVersion 1.0.0`, `coreVersion 3.16.3`). Файл едет вместе со сборкой ядра, поэтому появляется только после распаковки ядра в `prebuild/` (папка в `.gitignore`); свежая версия — по адресу `<адрес портала>/api/chartPlugin.d.ts`. **Перед любой правкой контрактных экспортов читать этот файл, а не догадываться.**

Контракт намеренно не раскрывает внутренние структуры (`config`, `field`, `axe`, `spec`, `data`, состояние редактора) — в ядре они на нетипизированном JS, все объявлены как `any`-псевдонимы. Их фактическую форму смотреть по коду плагина и по [defaultConfig.json](src/modules/CustomChart/model/defaultConfig.json).

Копия контракта лежит в [src/types/chartPlugin.d.ts](src/types/chartPlugin.d.ts) — импортируется как `import type { ... } from '../types/chartPlugin'` (в бандл типы не попадают). Файл — снимок конкретной версии контракта на момент копирования; при обновлении ядра сверять с актуальным `prebuild/api/chartPlugin.d.ts` и переносить изменения вручную. Проверка расхождения — скилл [`sync-contract`](.claude/skills/sync-contract/SKILL.md).

[docs/api](docs/api) в корне репозитория — более старый неформальный конспект. Он всё ещё полезен тем, чего в `.d.ts` нет: перечнем props и инжектов, которые ядро передаёт `CustomChart` (`datas`, `loadDatas`, `drillDown`, `changeMultipleGlobalFilterValueAndApply`, `hsTheme`, `commonWidgets`…), и списками конкретных имён секций/виджетов. При расхождении верить `.d.ts`.

## Команды

```bash
npm start
```

Dev-сервер (webpack-dev-server 6) на порту 7000 по умолчанию (переменная окружения `PORT` меняет порт — см. [webpack.config.js](webpack.config.js)). Требует распакованное **ядро ModusBI** в `prebuild/` — `devServer.static` раздаёт `prebuild/` статикой, а сам webpack-dev-server собирает и отдаёт `/plugins/custom_chart_0.js` на лету с HMR. Без `prebuild/` запуск бесполезен (и `prebuild/api/` тоже недоступен).

```bash
npm run build
```

Продакшен-сборка (`webpack --mode production`). `npm run build:dev` — несжатая сборка в режиме разработки.

```bash
npm run build:plugin
```

Создаёт дистрибутив `<manifest.name>.tar.gz`: копирует `build/custom_chart_0.js` → `plugin.js`, заменяет в первых 1000 символах `CustomChart0` на плейсхолдер `CustomChartNNN`, архивирует вместе с манифестом. Подстановку реального имени класса выполняет ядро по правилу `ReplacementInTheBody` из манифеста. Перед запуском положить `build/manifest.json` — шаблон в [manifest.example.json](manifest.example.json).

```bash
npm test
npm run test:watch
npx jest -t "имя теста"
npm run typecheck   # tsc --noEmit
```

Jest (v30, на `@swc/jest`, `testEnvironment: node`) подхватывает `*.spec.{js,jsx,ts,tsx}`. Спеки лежат рядом с кодом, не в `__tests__/`. Сейчас в репозитории только спеки каркаса: модель конфига (`getDefaultConfig`), `changeCustomChartReducer`, `DataAdaptor`, `ConfigEditor`, `CustomAxes`, `CustomChart`, `useChartSize`. Число спеков не фиксируем — оно растёт вместе с настройками нового плагина. Скрипт `test` запускается с `--passWithNoTests`: прогон не падает, когда спеков нет вовсе.

Разработка идёт через TDD двумя сабагентами с непересекающимися правами — см. «Работа ИИ-агентов».

Компонентные тесты возможны — стоят `@testing-library/react@12` (версия под React 16) и `jest-environment-jsdom`. Глобальное окружение остаётся `node`, поэтому спек с рендером открывается docblock'ом `/** @jest-environment jsdom */`; правки `jest.config.js` это не требует. UI-примитивы ядра приходят через проп `pluginImports` и в тестах заменяются заглушками.

Типы jest подключены через `types: ["jest"]` в [tsconfig.json](tsconfig.json). Поле задано явно: без него `tsc` не подхватывает `@types/*` автоматически и падает на `describe` с `TS2593`. Указание `types` отключает автоподключение остальных глобальных типов — при добавлении пакета с глобальными объявлениями его надо вписать в этот массив.

```bash
npm run lint
```

ESLint 10, flat config ([eslint.config.js](eslint.config.js)): `@eslint/js` + `typescript-eslint` recommended и `eslint-config-prettier` последним звеном, чтобы не конфликтовать с форматированием. `lint-staged` + husky (`.husky/pre-commit`) гоняют `prettier --write` и `eslint --max-warnings=0` на стейджинге. Prettier настроен ([.prettierrc](.prettierrc): 120 колонок, одинарные кавычки в т.ч. в JSX, trailing commas).

## Работа ИИ-агентов

Конфигурация команды лежит в `.claude/` и едет вместе с репозиторием: скиллы, сабагенты и хуки. Хуки объявлены в exec form: путь к правленому файлу приходит скрипту первым аргументом — Claude Code подставляет его сам через `args`, разбирать stdin не нужно.

### Требования не выдумываются

Правило действует раньше всех остальных — до выбора скилла, до первой строки кода, при анализе задачи наравне с разработкой. **Пробел в постановке заполняется вопросом, а не догадкой.**

Пробел — это когда:

- поведение не описано, а без него код не написать («добавь настройку прозрачности» — прозрачности чего, в каких единицах, что при 0);
- у формулировки два разумных прочтения, и они дают разный код;
- неизвестно, чего хочет пользователь как автор плагина: какая полка, какой тип пилюли, что показывать при пустых данных.

Как спрашивать: собрать **все** вопросы разом и задать до начала работы, а не выдавать по одному раз в полчаса. Каждый — с вариантами и своей рекомендацией, чтобы ответить можно было одним словом. Пока ждёшь ответа, делай ту часть, которая от него не зависит.

Чего не делать: додумывать «вероятно, имелось в виду», реализовывать оба варианта на всякий случай, прятать догадку в `TODO` и идти дальше, выдавать придуманное требование за согласованное.

**Согласованное требование записывается пятью полями.** Ответ пользователя — ещё не требование: устно сказанное «пусть будет прозрачность» через два прохода превращается в чью-то догадку. Перед началом работы требование фиксируется так, чтобы по нему можно было написать тест и потом проверить результат:

| Поле                | Что в нём                                                                          |
| ------------------- | ---------------------------------------------------------------------------------- |
| Вход                | какие полки заполнены, какие пилюли и сколько, какие настройки включены            |
| Ожидаемое поведение | что должно получиться — проверяемо, а не «стало удобнее»                           |
| Пустые данные       | полка не заполнена, выборка пуста, все значения `null`                             |
| Ошибка запроса      | бэкенд ответил ошибкой или не ответил вовсе                                        |
| Сохранённый конфиг  | что происходит с отчётом, сохранённым прошлой версией плагина, где нового поля нет |

Первые два поля — обычная постановка. Последние три в задачах не пишут почти никогда, а это три самых частых способа уронить плагин на портале: пустая выборка, отказ бэкенда и старый отчёт с новым кодом. Их значения такие же предмет согласования, как основное поведение, — и спрашиваются тем же списком вопросов, а не додумываются.

Требование, у которого нет ответа хотя бы на одно поле, в работу не берётся: это пробел, а с пробелом — к первому правилу этого раздела.

**Спрашивать — про решения, а не про факты.** Форма контракта лежит в `prebuild/api/chartPlugin.d.ts`, форма конфига — в `defaultConfig.json` и `plugin.types.ts`, форма ответа бэкенда — в реальном ответе. Это читается, а не уточняется у пользователя. Вопрос уместен там, где ответа нет в репозитории: продуктовое поведение, приоритеты, доступ к порталу.

### Скиллы

Шестнадцать скиллов лежат в [.claude/skills](.claude/skills); когда вызывать каждый, написано в его `description` — этот список сессия держит в контексте и без пересказа здесь. Ниже — только то, чего в описаниях нет: как скиллы соотносятся друг с другом.

`typescript-coding-standards` задаёт правила языка, `tdd` и `new-setting` — процесс; они дополняют друг друга, а не заменяют. `chart-shell` описывает разметку вокруг холста: у шаблона её нет вовсе — `CustomChart` рендерит голый контейнер, а ядро подложку плагину не рисует.

Три скилла отвечают за то, **куда** класть код и как вести папку: `custom-chart-module`, `custom-axes-module`, `custom-reducers-module`. Правила панели настроек живут в `new-setting` — отдельного скилла у `CustomSettings` нет.

Ещё три делят компонент по существу: `data-query-contract` — откуда берутся строки, `chart-lifecycle` — что происходит внутри холста, `chart-shell` — что нарисовано вокруг него. Все три нейтральны к библиотеке отрисовки; специфика конкретного движка выносится отдельно — для ECharts это `echarts-engine`.

`number-formatting` — единственный скилл про вывод чисел на экран: любое число из данных проходит через одну точку форматирования по правилам портала, а не через свой `toFixed` по месту.

`portal-integration-testing` закрывает то, чего не видят тесты: реальный ответ бэкенда, CSS портала, панель полок, сохранение конфига. Он отвечает за среду и матрицу проверок, `uc-testing` — за процесс прогона: UC пишется от требований, прогон идёт без правок, найденное разбирается отдельной фазой, повторно проверяется только задетое правками. Вызываются вместе; учётные данные в обоих вводит только пользователь. `package-plugin` собирает дистрибутив и проверяет архив; публикацией и версионированием он не занимается.

`migrate-to-typescript` работает в чужом репозитории — плагине пользователя, где этот шаблон служит образцом; пошаговый рецепт с готовыми конфигурациями лежит в [MIGRATION.md](MIGRATION.md).

### Сабагенты

Разработка идёт циклом TDD двумя агентами с **непересекающимися правами на файлы** — это и есть механизм, который не даёт подогнать тест под реализацию:

| Агент                                                                | Фаза             | Что правит                      |
| -------------------------------------------------------------------- | ---------------- | ------------------------------- |
| [`test-writer`](.claude/agents/test-writer.md)                       | RED              | только `*.spec.{js,ts,tsx}`     |
| [`implementer`](.claude/agents/implementer.md)                       | GREEN и REFACTOR | всё, кроме `*.spec.{js,ts,tsx}` |
| [`contract-reviewer`](.claude/agents/contract-reviewer.md)           | ревью контракта  | ничего, только чтение           |
| [`settings-flow-reviewer`](.claude/agents/settings-flow-reviewer.md) | ревью настроек   | ничего, только чтение           |

`contract-reviewer` запускать после правок контрактных экспортов, `CustomAxes` или `src/types/chartPlugin.d.ts`; `settings-flow-reviewer` — после правок в `CustomSettings/`, `CustomReducers/` или `defaultConfig.json`.

### Хуки

Оба объявлены в [.claude/settings.json](.claude/settings.json):

- **PreToolUse → [guard-paths.sh](.claude/hooks/guard-paths.sh)** запрещает `Edit`/`Write` внутри `prebuild/`. Каталог в `.gitignore` и перезаписывается при обновлении ядра — правка выглядит рабочей и исчезает бесследно. Контракт правится в `src/types/chartPlugin.d.ts`, код — в `src/`.
- **PostToolUse → [typecheck.sh](.claude/hooks/typecheck.sh)** гоняет `tsc --noEmit` после каждой правки `.ts`/`.tsx`. JSON-ответ сериализует `node` — вывод компилятора содержит кавычки и переводы строк, собирать такой ответ конкатенацией нельзя; Node доступен всегда, им же запускается `tsc`. CI в проекте нет, а `lint-staged` типы не проверяет — этот хук единственное, что ловит расхождение с контрактом сразу. Режима два: для обычного файла ошибки блокирующие, для `*.spec.*` и `*.d.ts` — предупреждение с подсказкой, потому что промежуточная некомпилируемость там штатна (фаза RED пишет тест на ещё не существующий экспорт, перенос контракта сходится только к концу).

Там же, в `settings.json`, разрешены без подтверждения команды проверки (`npm test`, `npm run typecheck`, `npm run lint`, `npm run build`, `npx jest/tsc/eslint/prettier`) и read-only команды git.

### Когда правки зацикливаются

Отдельное правило, потому что зацикливание — самый дорогой способ потратить сессию. Признак не в том, что задача сложная, а в том, что **правки идут, а состояние не улучшается**:

- одна и та же ошибка возвращается в новой формулировке;
- починка одного теста роняет другой, и обратно (пинг-понг);
- в коде копятся `as`, `any`, `@ts-expect-error`, `eslint-disable` — то есть чинится не причина, а её сообщение;
- правки уезжают в файлы, которые к исходной ошибке отношения не имели.

**Порог — три попытки.** Три правки одного и того же места, не давшие зелёного прогона, означают, что неверна гипотеза, а не код. Четвёртая правка запрещена: вместо неё —

1. **Откатить накопленное.** `git diff` показывает, что уже наворочено; `git checkout -- <файл>` или `git stash` возвращает к последнему зелёному состоянию. Диагностировать поверх слоя неудачных правок бессмысленно — половина ошибок уже своя собственная.
2. **Заменить догадку фактом.** Форму контракта смотреть в `prebuild/api/chartPlugin.d.ts`, а не выводить из имени метода. Форму данных — печатью реального объекта, а не рассуждением о том, каким он должен быть. Одиночный спек гонять точечно: `npx jest -t "имя теста"`.
3. **Разделить.** Проход, который тянет три требования сразу, отлаживается втрое дороже. Разбить на отдельные проходы цикла.
4. **Спросить пользователя.** Не «не получается», а: что пробовал (списком), какая ошибка держится дословно, две-три версии причины, какого знания не хватает — доступа к порталу, формы ответа бэкенда, решения о поведении.

Что **не** считается выходом из цикла: ослабить или удалить тест, заглушить типы через `any`/`as`/`@ts-expect-error`, отключить правило ESLint, добавить зависимость ради обхода, править `prebuild/` (хук всё равно запретит — и правильно сделает).

Отдельно: часть ошибок правкой кода не чинится в принципе, потому что они про окружение. Пример из этого проекта — `structuredClone is not defined` в спеке с `/** @jest-environment jsdom */`: функции нет в jsdom, и сколько ни правь реализацию, ошибка останется (см. «Запрещённые библиотеки»).

## Архитектура

### Семь экспортов — весь API плагина

[src/index.ts](src/index.ts) отдаёт ровно семь именованных экспортов; ядро импортирует каждый **статически**, поэтому отсутствующий экспорт ломает не первое обращение к нему, а соответствующую часть редактора целиком. Соответствие контракту `ChartPluginModule` проверяет тип `ContractCheck` в том же файле — расхождение роняет `npm run typecheck`, а не рантайм. Проверяется сам список экспортов (`import type * as Self from './index'`, самоссылка на модуль), поэтому удалённая строка `export` тоже даёт `TS2344`.

| Экспорт          | Как ядро его использует                                                                                   | Реализация                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `CustomChart`    | React-компонент + статический `getDefaultConfig()`, вызываемый при создании компонента до первого рендера | [CustomChart.tsx](src/modules/CustomChart/CustomChart.tsx)                            |
| `CustomReducers` | `(state, action, { autoApplySettings }) => state` под ключом `CHANGE_CUSTOM_CHART_N`                      | [changeCustomChartReducer.ts](src/modules/CustomReducers/changeCustomChartReducer.ts) |
| `CustomSettings` | компонент правой панели редактора                                                                         | [Settings.tsx](src/modules/CustomSettings/Settings.tsx)                               |
| `CustomAxes`     | объект с методами настройки панели осей                                                                   | [CustomAxes/index.tsx](src/modules/CustomAxes/index.tsx)                              |
| `DataAdaptor`    | `new DataAdaptor(data, config, spec, cacheId)` на каждый пересчёт данных                                  | [dataAdaptor.ts](src/modules/CustomChart/dataAdaptor.ts)                              |
| `SpecGenerator`  | `new SpecGenerator(type)` на каждый запрос                                                                | [specGenerator.ts](src/modules/CustomChart/specGenerator.ts)                          |
| `ConfigEditor`   | `new ConfigEditor()` без аргументов                                                                       | [configEditor.ts](src/modules/CustomChart/configEditor.ts)                            |

Тип компонента — строка `CustomChart0`…`CustomChart40` (плюс `CustomChartGraph`), подключается алиасом `custom-chart-N`. Бандл собирается один раз как `CustomChart0`; имя на реальный тип компонента меняется в два шага двумя разными сторонами: `create-plugin.js` при сборке дистрибутива подменяет `CustomChart0` → `CustomChartNNN` (плейсхолдер) в первых 1000 символах бандла, а ядро при установке плагина на портал заменяет `CustomChartNNN` на реальное имя класса по правилу `ReplacementInTheBody` из манифеста.

### Поток данных

```
config (полки, поля) → getQueryObjects → loadDatas (ядро) → props.data → DataAdaptor.remapData → plotData → CustomChart
```

Цепочку крутит сам компонент, а не ядро: **готового адаптора и готового `plotData` в props нет**. Ядро отдаёт сырой ответ бэкенда в `data` (`{ fetching, data, cached, cropped, error, errorMsg, msg }` — поля `error`/`errorMsg` и есть штатный способ узнать про отказ бэкенда), а адаптор каждый компонент строит сам и держит в своём состоянии — так устроен и штатный хост плагинных типов в ядре (метод `getChartData` в `prebuild/app.*.js`). [CustomChart.tsx](src/modules/CustomChart/CustomChart.tsx) повторяет эту механику: определяет `datasetId` (`getDatasetId`), собирает `queryObjects` (`DataAdaptor.getQueryObjects`), пока `data` нет — зовёт инжект `loadDatas(datasetId, null, config.filters, queryObjects, { editor, componentId })` (второй аргумент всегда `null`; есть и шестой — `cacheId`, см. ниже), а после ответа строит адаптор через [ComponentTypeManager](src/managers/ComponentTypeManager.ts), как ядро (`new Manager(type).getDataAdaptor(data, config, spec, cacheId)`). Конструктор `DataAdaptor` сам зовёт `refresh` → `remapData`, поэтому `plotData` готов сразу после `new`; пересборка идёт только при смене данных или конфига, а не на каждый рендер.

**Первый разрыв цепочки — не здесь, а в `ConfigEditor`.** Его `addField`/`addAllFields`/`updateField` возвращают конфиг без изменений, а ядро кладёт возвращённое как новый `configDraft`, — значит брошенная на полку пилюля теряется, `getDatasetId` отдаёт `undefined`, и эффект компонента выходит **до** вызова `loadDatas`. Запрос сейчас не уходит вовсе. Порядок доработки: `ConfigEditor` → `CustomAxes.sortAxes` (тоже отдаёт `[]`, то есть пустую панель полок) → `getQueryObjects` → `remapData`.

**Ловушка `cacheId`.** Коннектор ядра считает `props.cacheId` по **своим** `queryObjects` (штатным `CommonDataAdaptor.getQueryObjects`), а `loadDatas` — по тем, что передал плагин. Разошлись — ответ ложится в другую ячейку, и `props.data` не появится никогда. Штатный выход: передать `props.cacheId` шестым аргументом `loadDatas` (он перекрывает расчёт). У этого решения есть побочный эффект, снятый на портале: **ответ тогда приходит не в проп `data`, а в `props.datas[cacheId]`** — компонент читает оба места (`data || datas?.[cacheId]`), потому что путь через `data` остаётся рабочим, когда ядро `cacheId` не передало. Там же, в скилле, — автообновление данных: тумблер «Автообновление» пишет `config.refresh`/`config.refreshTime`, но таймер перезапроса ядро за плагин не заводит, и идёт перезапрос инжектом `reloadDatas`, а не `loadDatas`. Подробности — скилл [`data-query-contract`](.claude/skills/data-query-contract/SKILL.md).

`getQueryObjects` и `remapData` в [dataAdaptor.ts](src/modules/CustomChart/dataAdaptor.ts) — заглушки: форма цепочки загрузки собрана, содержания в ней нет. Это **обязательный пункт** доработки нового плагина:

- `getQueryObjects(config)` должен собрать из полок конфига описание запроса к бэкенду — какие поля идут в `select`, что в `group by`, какие фильтры и агрегации применить. Пока метод возвращает пустой массив, `loadDatas` уходит с пустым запросом и данных не будет.
- `remapData(config)` должен привести `this.aggregated` (массив трейсов, по одному на пилюлю полки «Значения») к строкам `plotData`, которые понимает отрисовка. Первое, обо что спотыкаются: ключи ответа бэкенда приходят алиасами вида `[categories]`, `[categories][0]` — скобки ядро снимает только у части из них (`categories`, `series`, `identity`, `linkage`, `node`), остальные остаются с квадратными скобками в имени ключа. Алиаса `[details]` при этом не существует: полка «Детали» уходит в запрос как `[values]`, то есть отдельным трейсом.

Полученный `plotData` лежит в состоянии адаптора компонента, но на экран сейчас не выводится — `CustomChart` рендерит пустой `div` с отладочными атрибутами `data-size` (размер из `useChartSize`) и `data-rows` (число строк `plotData`, пока всегда `0` — `remapData` заглушка), это не визуализация, а след для DevTools. Подключая свою библиотеку отрисовки вместо пустого контейнера, сохрани три вещи, на которые уже завязан компонент: контейнер с `ref`, размер из [useChartSize](src/modules/CustomChart/hooks/useChartSize.ts) (библиотеке отрисовки он обычно нужен для `resize()`) и работу с данными в эффекте — запрос через `loadDatas` и сборку адаптора из `props.data`.

### Раскладка модуля CustomChart

Папку файла определяет его род, а не тема:

```
src/modules/CustomChart/
  index.ts               публичный контракт модуля: единственная дверь наружу
  CustomChart.tsx        компонент
  dataAdaptor.ts         ┐
  specGenerator.ts       ├ контрактные единицы: их создаёт ядро
  configEditor.ts        ┘
  model/                 типы, конфиг, чистые преобразования данных
  ui/                    React-компоненты, кроме самого CustomChart
  hooks/                 React-хуки
  lib/                   чистые функции без React и без DOM
  engine/                мост к библиотеке отрисовки (появляется вместе с ней)
```

Правила раскладки целиком — скилл [`custom-chart-module`](.claude/skills/custom-chart-module/SKILL.md): он источник истины по тому, куда класть файл, смежные скиллы говорят, что написать. Там же — почему нет папки `utils/`, зачем модулю единственный `index.ts` и почему `ComponentTypeManager` адресует файлы модуля напрямую.

### Конфигурация компонента

[defaultConfig.json](src/modules/CustomChart/model/defaultConfig.json) — форма `config`, которую ядро хранит в отчёте и отдаёт обратно: плоский объект с параметрами компонента (`title`, `chartType`, `precision`, `margin`, `outline`…) плюс массив `axes` — пять полок, каждая со своим `type`: `values`, `categories`, `series`, `details`, `filters`. Ёмкость полки задаёт её `selectedFieldIndex`: `-2` — несколько пилюль, `0` — ровно одна, `-1` — полка отключена. Изменения дефолтов надо согласовывать с `CustomAxes` — там же читаются те же поля осей.

Типизированное зеркало этой формы — `ChartConfig` в [plugin.types.ts](src/modules/CustomChart/model/plugin.types.ts). Два поля объявлены в типе, но в JSON их нет: `filters` (значения фильтров компонента — их наполняет редактор, а ядро кладёт третьим аргументом в `loadDatas`) и `rowsLimit`. Дефолты отдаёт [getDefaultConfig.ts](src/modules/CustomChart/model/getDefaultConfig.ts) — свежей копией через `structuredClone` на каждый вызов: ядро вправе править полученный объект.

### CustomAxes: «необязательно» ≠ «по умолчанию»

Все 11 методов модуля контрактно необязательны, но отсутствующий метод возвращает `undefined`, что для большинства означает **«пусто»** — полка без имени, скрытая пилюля, пустая панель осей. Ядро не падает, в dev-сборке пишет предупреждение в консоль, а редактор выглядит сломанным. Шаблон реализует десять методов из одиннадцати ([CustomAxes/index.tsx](src/modules/CustomAxes/index.tsx)); не реализован намеренно только `getPillTypeOptions` — по контракту его отсутствие означает «использовать штатный список ядра».

Два факта про контекст, на которых спотыкаются чаще всего: `componentType` ядро передаёт девяти методам из одиннадцати, а `isVisibleAxe` и `getPillTypeOptions` его не получают вовсе; `isVisibleAxeDragItemMenuOption` вызывается порядка 28 раз за один рендер меню пилюли — держать её дешёвой.

Остальное — скилл [`custom-axes-module`](.claude/skills/custom-axes-module/SKILL.md): что на самом деле делает `isDisabledAxe` и почему решение выводится из ёмкости полки, почему `getPillTypeOptions` сверяет `axisType`, а не `axisName`, что лежит в контексте меню пилюли.

### Настройки → редьюсер

У шаблона пока нет ни одной своей настройки: [Settings.tsx](src/modules/CustomSettings/Settings.tsx) рендерит `null`, а [changeCustomChartReducer.ts](src/modules/CustomReducers/changeCustomChartReducer.ts) возвращает состояние без изменений. Оба файла несут комментарий с рабочей версией — по нему восстанавливается механика.

Механика (когда настройка появится): компоненты в `src/modules/CustomSettings/` не мутируют config сами — они вызывают `changeChart('<command>', { value })`, а редьюсер обрабатывает строковую команду через таблицу «команда → путь в конфиге» (`COMMANDS`, без веток `if`), правя копию `component.configDraft`.

**Результат обязан пройти через `options.autoApplySettings(state)`** — это функция ядра, а не флаг: без неё правка осядет в `configDraft` и не доедет до компонента. Она же учитывает режим ручного применения (`manualApplySettings`), помечая черновик как dirty вместо немедленного применения.

Пять точек, в которых живёт настройка, шаблоны четырёх контролов, чтение конфига в секции и работа со старыми отчётами — скилл [`new-setting`](.claude/skills/new-setting/SKILL.md); устройство редьюсера — [`custom-reducers-module`](.claude/skills/custom-reducers-module/SKILL.md). Одна ловушка стоит того, чтобы знать её заранее: **готовые секции ядра из `pluginImports.sections` пишут своё поле в `configDraft` собственными колбэками, в обход `changeChart` и таблицы `COMMANDS`** — записи в таблице им не нужно.

UI-примитивы и готовые блоки настроек не импортируются — они приходят из ядра через проп `pluginImports`, у которого три раздела:

- `pluginImports.sections` — готовые секции ядра (`DataOptionsContent`, `FilterModeOptionsContent`, `DrillOutOptionsContent`, `DescriptionOptionsContent`, `OutlineOptionsContent`, `titleTextFieldContent`, `precisionSliderContent`…);
- `pluginImports.components` — UI-компоненты (`SettingsSection`, `SettingsItem`, `SettingsToggle`, `SettingsSlider`, `SettingsColorPicker`, `SettingsMultiselect`…);
- `pluginImports.services` — сервисы ядра, в частности сервис модальных окон. В шаблоне пока не используется.

Ядро передаёт `CustomSettings` также `component` (с `type`, `config`, `spec`, `configDraft`), `data`, `reportOptions` и `reportlist`.

## Соглашения

- `src/modules/**`, `src/managers/` и `src/index.ts` — на TypeScript (`strict: true`, сборка через `swc-loader`, JSX — classic runtime).
- Опции SWC лежат в одном месте — [swc.config.js](swc.config.js); `webpack.config.js` и `jest.config.js` берут пресет оттуда и задают только свой `target` (`es2018` для браузерного бандла, `es2022` для тестов в node). Правило «JSX только classic» живёт там же: automatic runtime подтянул бы `react/jsx-runtime`, которого нет в `externals`.
- Стилей в шаблоне нет, но пайплайн собран: `.scss`/`.css` проходят `sass-loader` → `css-loader` → `style-loader`, то есть инлайнятся в бандл — ядро подключает плагин одним JS-файлом, отдельный CSS подключать некому. Side-effect импорты объявлены в [src/types/styles.d.ts](src/types/styles.d.ts), в тестах глушатся через `moduleNameMapper` → `test/styleMock.js`.
- Библиотеки отрисовки в шаблоне нет — `CustomChart` рендерит пустой контейнер (см. «Поток данных»). Часть библиотек портал раздаёт глобально, подключая их скриптом до плагинов (так сделано с ECharts). Отсюда развилка: либо плагин берёт версию портала и объявляет библиотеку внешней, либо ставит свою — и тогда обязан изолировать её от глобальной модульным импортом. Смешивать пути нельзя: получатся два экземпляра библиотеки на странице. Подробности для ECharts — скилл `echarts-engine`, общий жизненный цикл холста — `chart-lifecycle`.
- Общие типы панели настроек (`ChangeChart`, тип props секции) заводятся в `src/modules/CustomSettings/types.ts` — файла пока нет (нет ни одной секции, которой он нужен), заводится вместе с первой секцией, а не по копии в каждом компоненте.
- Алиасов и нестандартных правил резолва модулей в проекте нет — все импорты относительные.
- Тексты интерфейса — русские строковые литералы прямо в JSX.

### Запрещённые библиотеки

**`react-addons-update` не использовать.** Пакет заброшен, официально заменён на `immutability-helper` и тянет за собой legacy-обвязку React. В проекте его нет ни в зависимостях, ни в коде — так и оставить. Встретишь в коде, скопированном из ядра, — убирай: неглубокие правки конфига делаются обычным спредом, глубокие — клонированием (см. ниже).

**`_.cloneDeep` в новом коде не использовать** — предпочитать нативный `structuredClone`. Лишняя обёртка над тем, что есть в платформе, а `lodash` в бандле оплачивается размером. Рантайм-зависимостей у шаблона нет: `lodash` придётся добавить осознанно, если он понадобится, — образец записи по пути в комментарии `changeCustomChartReducer.ts` обходится без него. Единственная согласованная зависимость плагина, выросшего из шаблона, — `dompurify` для очистки HTML описания на обороте компонента (скилл [`chart-shell`](.claude/skills/chart-shell/SKILL.md)).

В `changeCustomChartReducer.ts` рабочая версия (см. комментарий в файле) клонирует `configDraft` через `structuredClone` — то же правило: `_.cloneDeep` можно там, где подходит структура, `structuredClone` предпочтительнее.

Подходит не всякая: `structuredClone` ведёт себя иначе, чем `_.cloneDeep`, и разница молчаливой не бывает.

| Что клонируем                  | `_.cloneDeep`      | `structuredClone`                         |
| ------------------------------ | ------------------ | ----------------------------------------- |
| Функции в объекте              | копирует по ссылке | бросает `DOMException` (`DataCloneError`) |
| Экземпляр класса               | сохраняет прототип | отдаёт обычный `Object`                   |
| `Date`, `Map`, `Set`, `RegExp` | копирует           | копирует                                  |
| Ключи со значением `undefined` | сохраняет          | сохраняет                                 |
| React-элементы, DOM-узлы       | копирует по ссылке | бросает                                   |

Отсюда практическое правило: `structuredClone` — для данных (`config`, `configDraft`, `plotData`, ответы ядра), `_.cloneDeep` остаётся там, где в структуре могут оказаться функции, React-элементы или экземпляры классов — например состояние, которое ядро передаёт компоненту вперемешку с колбэками.

**Ловушка в тестах:** в jsdom-окружении `structuredClone` отсутствует (проверено на jsdom 26.1.0) — спек с docblock'ом `/** @jest-environment jsdom */` упадёт на `structuredClone is not defined`. В окружении `node`, которое стоит по умолчанию, функция есть. Тестируешь код с `structuredClone` в компонентном спеке — добавляй полифилл в этот файл или проверяй логику отдельным тестом в `node`-окружении.

Типы в порядке: `structuredClone` объявлен в `lib.dom`, который уже подключён в [tsconfig.json](tsconfig.json).
