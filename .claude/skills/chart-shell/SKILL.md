# Подложка компонента визуализации

## Суть

Подложка — всё, что вокруг холста: контейнер, шапка, оборот с описанием, оверлеи. Ядро ModusBI
рисует её штатным диаграммам само, **кастомному плагину — нет**. Плагин обязан воспроизвести
разметку ядра: тогда оформление приходит из CSS портала, а компонент неотличим от штатных.

В шаблоне подложки нет вовсе — `src/modules/CustomChart/CustomChart.tsx`
рендерит один пустой `div` с `ref` и отладочными атрибутами. Скилл описывает, что вокруг него
вырастает.

Подложка собирается **из чистых функций**: каждый её кусок — функциональный компонент,
зависящий только от пропов. Побочные эффекты (инстанс библиотеки отрисовки, подписки, таймеры)
живут во владельце холста — самом `CustomChart`. Функция подложки ничего не знает про рисование.

## Из чего состоит

```
div.hsChartContainer            ← контейнер: id, фон плашки, колонка
├── div.componentHeader         ← шапка (функция от config и темы)
│   ├── span
│   │   ├── div.titleText.strongly.nowrap
│   │   └── div.subtitleText.nowrap
│   └── span.path               ← пустой, в штатных туда идёт путь детализации
└── div.componentBody           ← тело: даёт холсту высоту
    ├── div.componentContainer  ← сюда отрисовка, единственный узел с ref
    ├── div.backSide            ← оборот с описанием
    ├── оверлей предупреждения
    └── оверлей статуса
```

Порядок внутри тела задан: холст первым — он единственный, чей узел нельзя ни пересоздать, ни
переставить; `backSide` за ним — портал показывает его по своему `z-index`, а не по месту в
потоке; оверлеи последними, чтобы лежать поверх холста.

Классы корня пишутся в том же порядке, что у ядра: **`hsChartContainer` первым, свой класс
плагина (`hs` + имя визуализации) вторым** — `["hsChartContainer", "amCharts4"]`,
`"hsChartContainer hsSwitchControlPanel"` и так во всех штатных компонентах. На CSS порядок не
влияет, но разметка должна совпадать с ядром буквально: по ней ищут узлы пользовательские темы.

**`ref` переезжает с корня на `componentContainer`.** Сейчас он на корне, и
`useChartSize` (`src/modules/CustomChart/hooks/useChartSize.ts`) меряет весь компонент вместе с шапкой.
Библиотеке отрисовки нужен размер холста, а не компонента, — иначе диаграмма окажется выше
доступного места ровно на высоту шапки (38 px и больше).

## Классы: что даёт CSS портала

Набор правил задаёт CSS портала, и он меняется вместе с ядром — на слово не доверять,
проверять в своей сборке:

```bash
grep -o "\.hsChartContainer[^{]*{[^}]*}" prebuild/*.css prebuild/css/*.css
```

| Класс                    | Что приходит из ядра                                                                                      |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| `hsChartContainer`       | `display:flex; flex-direction:column; height:100%; width:100%; position:relative`                         |
| `componentHeader`        | `min-height:38px; flex-basis:38px; overflow:hidden` — плюс отступы и позиционирование, см. ниже           |
| `componentHeader > span` | колонка из заголовка и подзаголовка                                                                       |
| `titleText`              | обрезка в две строки с многоточием (`-webkit-line-clamp:2`)                                               |
| `subtitleText`           | одна строка с многоточием                                                                                 |
| `backSide`               | скрыт (`opacity:0; z-index:-1`); ядро показывает его, добавляя `flipped` на панель по кнопке «Информация» |

**Оборот не виден в редакторе компонента вовсе:** `.hsComponentEditor .hsChartContainer .backSide { display: none }`. Проверять описание нужно в отчёте, а не в редакторе, — иначе увидишь пустоту и решишь, что сломал разметку.

**Бесклассовых правил `.componentHeader` в сборке несколько (в 3.16.3 — семь), и они не согласованы между собой.** Один вариант — статический флекс с `padding: 0 60px 0 16px` (тот самый правый отступ под кнопки ядра), другой — `position: absolute; top/left/right: 0; z-index: 1600; pointer-events: none; padding: 0 16px`, то есть шапка вообще не участвует в колонке. Какое победит, решает порядок загрузки ленивых чанков отчёта, а не специфичность, — прочитать это из CSS нельзя.

Практический вывод: разметку делай по колоночной модели (шапка в потоке, тело растянуто), а **в портале первым делом посмотри в DevTools computed-стиль шапки**. Если `position: absolute` — тело придётся отодвинуть сверху на высоту шапки; если статический флекс — всё сходится само.

То же и с `.componentContainer`: правил тоже несколько, и часть даёт `position: absolute` **без** `inset`. Холст на таком правиле схлопнется в ноль, а `useChartSize` вернёт `0×0`, поэтому `CONTAINER_STYLE` задаёт `position: absolute; top: 0; right: 0; bottom: 0; left: 0` сам, не полагаясь на CSS портала.

А вот `componentBody`, `path`, `strongly` и `nowrap` **правил CSS в ядре не имеют**: ядро ставит
их в разметке, но оформления не задаёт. Ставить их всё равно нужно — разметка должна совпадать с
ядром, по ним же ищут узлы тесты и пользовательские темы, — но высоту и позиционирование тела
подложка задаёт себе сама.

Своих отступов, шрифтов и выравнивания шапке не задавать — портал уже всё описал. Инлайновые
стили только там, где CSS ядра молчит: тело (`position:relative; flex:1 1 auto; min-height:0`),
фон плашки, цвета текста из темы.

## Функции-строители

Одна функция — один узел. Возвращает `null`, когда узел не нужен: условие видимости живёт внутри
функции, а не в вызывающем `render`.

Раскладка задана скиллом `custom-chart-module`: компоненты подложки — `ui/` (`ui/ChartHeader.tsx`,
`ui/ChartBackSide.tsx`, `ui/ChartWarning.tsx`, `ui/ChartPlaceholder.tsx` — оверлей статуса, `ui/ChartErrorBoundary.tsx`), `getLocal` и прочие
чистые функции без React — `lib/`. В корне модуля остаются только точки входа, наружу через
`index.ts` подложка не выводится: она внутреннее дело модуля. Спек — рядом со своим файлом.

```tsx
const ChartHeader = ({ config, locale, subheader, colors }: ChartHeaderProps) => {
  if (config.showtitle === false) return null;

  const title = getLocal(config, 'title', locale);
  const subtitle = subheader || getLocal(config, 'subtitle', locale);
  if (!title && !subtitle) return null;

  return (
    <div className='componentHeader'>
      <span>
        {title ? (
          <div
            className='titleText strongly nowrap'
            style={{ color: colors.title }}
          >
            {title}
          </div>
        ) : null}
        {subtitle ? (
          <div
            className={['subtitleText', title && 'nowrap'].filter(Boolean).join(' ')}
            style={{ color: colors.subtitle }}
          >
            {subtitle}
          </div>
        ) : null}
      </span>
      <span className='path' />
    </div>
  );
};
```

`classnames` в проекте нет и добавлять его ради одной строки не нужно — `filter(Boolean).join(' ')`
делает то же. `nowrap` означает «текст ужимается в одну строку, потому что рядом есть соседняя»:
у подзаголовка он ставится, только когда над ним есть заголовок; у заголовка стоит всегда — в
ветке с непустым заголовком условие шаблона истинно по построению.

Корень собирает их композицией — без веток и тернарников в JSX:

```tsx
<div
  className='hsChartContainer hsMyPlot'
  id={componentId === undefined ? undefined : `container_${componentId}`}
  style={{ backgroundColor: config.bgColor || undefined }}
>
  <ChartHeader
    config={config}
    locale={locale}
    subheader={subheader}
    colors={headerColors}
  />
  <div
    className='componentBody'
    style={BODY_STYLE}
  >
    <div
      className='componentContainer'
      ref={containerRef}
      style={CONTAINER_STYLE}
    />
    <ChartBackSide
      config={config}
      locale={locale}
    />
    <ChartWarning text={warning} />
    <ChartPlaceholder
      status={status}
      message={message}
    />
  </div>
</div>
```

`BODY_STYLE` и `CONTAINER_STYLE` — константы модуля, а не литералы в JSX: объект, созданный в
теле компонента, на каждом рендере новый и рвёт мемоизацию у всего, что ниже.

## Статус компонента: одно перечисление на всю подложку

Оверлей статуса и холст — две ветки одного решения, а не два независимых условия. Поэтому
статус вычисляется **один раз**, отдельным значением, и по нему решают все: и оверлей, и
владелец холста.

Набор, покрывающий то, с чем плагин сталкивается на портале:

| Статус       | Когда                                              | Что видит пользователь        |
| ------------ | -------------------------------------------------- | ----------------------------- |
| `loading`    | `data.fetching`                                    | индикатор загрузки            |
| `needAxe`    | обязательная полка не заполнена                    | подсказка, какую полку занять |
| `queryError` | `data.error` / `data.errorMsg` — бэкенд отказал    | сообщение об ошибке запроса   |
| `noData`     | ответ пришёл, строк нет                            | «нет данных»                  |
| `badData`    | строки есть, но непригодны (все `null`, ноль сумм) | сообщение с причиной          |
| `ready`      | всё остальное                                      | холст                         |

Три из шести — это ровно те поля требования, которые в задачах не пишут (CLAUDE.md, «Требования
не выдумываются»): пустые данные, ошибка запроса, непригодные данные. Заводя статус, спрашивай
их формулировки у пользователя, а не сочиняй тексты сообщений.

Источник истины по статусу — **состояние запроса**, а не модель данных: модель не знает, идёт
ли загрузка и ответил ли бэкенд. Поэтому статус считается там, где виден `props.data`, и
передаётся вниз, а не вычисляется заново в каждом компоненте подложки.

**Вне статуса `ready` инстанс библиотеки отрисовки освобождается** — иначе под сообщением
«нет данных» остаётся устаревшая диаграмма. Узел контейнера при этом не пересоздаётся (см.
таблицу ошибок ниже), освобождается именно инстанс: подробности — `chart-lifecycle`.

## Граница ошибок: падение отрисовки не роняет отчёт

Компонент оборачивается собственной границей ошибок (`ui/ChartErrorBoundary.tsx`). Причина
прикладная: страница отчёта держит несколько компонентов, и исключение внутри библиотеки
отрисовки одного из них без границы снимает с экрана **все** — пользователь видит белый отчёт
вместо одной сломанной плитки.

Граница — единственный случай, когда в TS-части плагина заводится классовый компонент помимо
контрактных единиц: в React 16 `componentDidCatch` / `getDerivedStateFromError` бывают только
у классов. Это исключение из правила «классов минимум» (скилл `typescript-coding-standards`),
и оно уже согласовано.

Что граница ловит, а что нет: исключения рендера дочернего дерева — да; ошибки в асинхронных
колбэках движка, в обработчиках событий и в эффектах — нет. Поэтому граница не заменяет
проверку данных: непригодные строки отсекаются статусом `badData` до отрисовки, а не ловятся
границей после падения.

## Откуда берутся данные подложки

| Что               | Источник              | Чем читать                                                                          |
| ----------------- | --------------------- | ----------------------------------------------------------------------------------- |
| Заголовок         | конфиг отчёта         | `getLocal(config, 'title', locale)` — перевод лежит в `title__<язык>`               |
| Подзаголовок      | выборка, иначе конфиг | `subheader` последней строки `plotData` \|\| `getLocal(config, 'subtitle', locale)` |
| Показывать шапку  | конфиг                | `config.showtitle !== false`                                                        |
| Описание оборота  | конфиг отчёта         | `getLocal(config, 'description', locale)`                                           |
| Цвет заголовка    | тема портала          | `hsTheme?.palette?.secondaryTextColor`                                              |
| Цвет подзаголовка | тема портала          | `hsTheme?.palette?.componentSubtitleTextColor ?? hsTheme?.palette?.disabledColor`   |
| Фон плашки        | конфиг                | `config.bgColor` — на **корень**, не на холст                                       |
| Идентификатор     | проп ядра             | `componentId` → `id="container_<id>"`                                               |

**Ключа `componentSubtitleTextColor` в поставляемых темах нет** (`grep -c componentSubtitleTextColor prebuild/json_themes/baseTheme.json` → 0): он встречается только в ветках под флагом продукта. Без фолбэка на `disabledColor` подзаголовок получит `color: undefined`. Все обращения к теме — через опциональную цепочку: ядро вправе не передать `hsTheme`, и падать из-за этого компонент не должен.

`showtitle`, `title`, `subtitle`, `bgColor` уже объявлены в `ChartConfig`
(`src/modules/CustomChart/model/plugin.types.ts`) и лежат в
`src/modules/CustomChart/model/defaultConfig.json`. Поля `description` там нет —
заводя оборот, добавь его в `ChartConfig` (и дефолт в JSON, если он нужен).

`hsTheme` и `locale` ядро передаёт компоненту (перечень props — `docs/api`), но
в `CustomChartProps` шаблона они не объявлены: там перечислено только то, что шаблон читает.
Дописать их в интерфейс — часть работы, а не побочный эффект.

## Локализация: `getLocal` пишется свой

Готовой функции у плагина нет — `helpers` ядра контрактом не раскрыты. Семантика ядра
(`app.*.js`, `getLocal`) простая, повторяется в пять строк и не тянет зависимостей. Место
функции — `src/modules/CustomChart/lib/getLocal.ts`: про конфиг она не знает, работает с любым
объектом, тестируется в окружении `node`:

**Сигнатура намеренно отличается от ядровой.** У ядра `getLocal(source, key, rawFlag)`: язык берётся из глобального синглтона, а третий аргумент — флаг «вернуть только перевод». Плагину эта глобаль недоступна, поэтому язык приходит аргументом. Расхождение осознанное, и его место — в JSDoc функции: иначе следующий читатель примет её за дословную копию ядра.

```ts
/**
 * Локализованное значение поля конфига: перевод лежит в `<ключ>__<язык>`, иначе базовое поле.
 * В ядре язык берётся из глобальных настроек; плагину он приходит пропом, поэтому здесь он аргумент.
 */
export const getLocal = (source: Record<string, unknown>, key: string, locale?: string): string => {
  const localized = locale ? source[`${key}__${locale}`] : undefined;
  const value = localized === undefined || localized === null ? source[key] : localized;
  return value === undefined || value === null ? '' : String(value);
};
```

Читать `config.title` напрямую — самая частая ошибка: у отчёта с переводами заголовок молча
подменяется исходным языком.

## Оборот: HTML через санитайзер

Описание ядро хранит **как HTML** — в редакторе описания есть форматирование, и в конфиг ложится
разметка вида `<p>Отчёт по <b>выручке</b></p>`. Ядро выводит её `dangerouslySetInnerHTML`,
прогнав через свой санитайзер; плагину этот санитайзер недоступен — `helpers` ядра контрактом
не раскрыты.

**Решение проекта: свой санитайзер, DOMPurify.**

```tsx
import DOMPurify from 'dompurify';

const html = DOMPurify.sanitize(getLocal(config, 'description', locale));
// …
<div
  className='backSide'
  dangerouslySetInnerHTML={{ __html: html }}
/>;
```

Почему так, а не иначе:

| Вариант                               | Чем плох                                                                                        |
| ------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Вывести текстом                       | отформатированное описание показывается вместе с тегами — выглядит как сломанный плагин         |
| `dangerouslySetInnerHTML` без очистки | описание пишет один пользователь портала, а смотрит другой: чужой HTML исполняется в его сессии |

Это **единственная рантайм-зависимость, которую шаблон разрешает добавить** (около 20 КБ в
бандл). Правило «никаких новых зависимостей без обсуждения» из `typescript-coding-standards`
на неё не распространяется — обсуждение уже состоялось. Всё остальное по-прежнему добавляется
только осознанно.

Санитайзить нужно **каждый** вывод чужой разметки, а не только оборот: появится ещё одно поле
конфига с HTML — прогоняй через ту же функцию.

## Частые ошибки

| Ошибка                                                               | Чем оборачивается                                                                                                       |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Своя вёрстка шапки вместо классов ядра                               | компонент выглядит чужим: другой шрифт, отступы, нет обрезки длинного заголовка                                         |
| Компоненты подложки в корне модуля                                   | корень перестаёт отвечать на вопрос «где точки входа»; их место — `ui/`, см. `custom-chart-module`                      |
| `ref` остался на корне                                               | `useChartSize` возвращает высоту вместе с шапкой, диаграмма не влезает                                                  |
| Фон `config.bgColor` задан только холсту                             | плашка красится под холстом, а шапка остаётся на прежнем фоне                                                           |
| Заголовок из `config.title` напрямую                                 | теряется перевод: ядро хранит его в `title__<язык>`                                                                     |
| Оверлеи на уровне корня                                              | накрывают шапку; их место — внутри `componentBody`                                                                      |
| Контейнер холста пересоздаётся при смене статуса                     | библиотека теряет свой DOM; прятать через `visibility:hidden`, никогда `display:none` — иначе размеры схлопнутся в ноль |
| Забыть `backSide`                                                    | описание из секции «Инфо» негде показать, кнопка «Информация» переворачивает пустоту                                    |
| Забыть `id="container_<id>"`                                         | ядро не находит компонент снаружи                                                                                       |
| Добавить `classnames` или `lodash` ради подложки                     | заводить зависимость ради `join(' ')` незачем; единственная согласованная — `dompurify` для оборота                     |
| Описание выведено `dangerouslySetInnerHTML` без `DOMPurify.sanitize` | чужой HTML из отчёта исполняется в сессии читателя                                                                      |

## Чего скилл не покрывает

Цвета оверлеев (фон плейсхолдера, палитра баннера предупреждения) своих токенов в теме портала
не имеют — их задаёт сам плагин. Появится соответствие токену — перевести их на тему тем же
путём, что цвета шапки.

Настройки панели редактора, которые управляют подложкой (переключатель заголовка, выбор цвета
плашки), заводятся не здесь: порядок — в скилле `new-setting`.

## Проверка

Разработка идёт циклом TDD (скилл `tdd`): тесты пишет `test-writer`,
разметку — `implementer`.

Спек кладётся рядом с компонентом и открывается docblock'ом `/** @jest-environment jsdom */` —
глобальное окружение проекта `node`. Проверяются структура и условия видимости: шапка исчезает
при `showtitle: false`, при пустых заголовке и подзаголовке узла нет, `nowrap` у подзаголовка
появляется только вместе с заголовком, `id` собирается из `componentId`. Оформление проверять
тестами бессмысленно — CSS портала в jsdom нет.

Поэтому подложку смотрят **в портале**: распакованное ядро в `prebuild/`, `npm start` (порт 7000),
открыть отчёт с компонентом и сверить — шапка на месте и на общей плашке, кнопки ядра справа
нажимаются (тот самый отступ `60px`), кнопка «Информация» переворачивает компонент к описанию,
длинный заголовок обрезается многоточием, а не ломает раскладку.
