# ECharts как движок отрисовки

## Суть

Скилл описывает **только специфику ECharts**. Жизненный цикл холста — создание, обновление,
размер, подписки, уничтожение, клики и drill — задаёт `chart-lifecycle`; здесь реализуется
его интерфейс `ChartEngine` и разбираются ловушки, которых нет у других движков. Жизненный
цикл оттуда действует целиком: инстанс уничтожается в `cleanup`, подписки снимаются там же.

Читать после `chart-lifecycle`, а не вместо него.

## ECharts на портале уже есть

Портал подключает ECharts **глобальным скриптом до скриптов плагинов**: файл лежит рядом со
слотами плагинов (`plugins/echarts.min.js`), и к моменту загрузки плагина на странице есть
`window.echarts`. Ядро своими диаграммами пользуется именно ей, через `globalThis.echarts`.

Отсюда развилка, с которой начинается интеграция: **брать библиотеку у портала или ставить
свою**. Версию портала смотреть в распакованном ядре, а не принимать на веру:

```bash
grep -o "plugins/echarts.min.js" prebuild/index.html
grep -o 'version[:=]"[0-9.]*"' prebuild/plugins/echarts.min.js | sort -u | head
```

## Развилка: библиотека портала или своя

| Что берём          | Вес бандла  | Версия                         | Чем платим                                                  |
| ------------------ | ----------- | ------------------------------ | ----------------------------------------------------------- |
| Библиотеку портала | 0           | та, что стоит на портале       | плагин ломается, когда портал обновит или уберёт библиотеку |
| Свою               | +150–400 КБ | зафиксирована в `package.json` | вес бандла; требует изоляции от глобальной — см. ниже       |

### Берём версию портала

Путь по умолчанию в шаблоне — **не этот** (см. итог развилки ниже); комментарий в
`webpack.config.js` над `externals` описывает именно тот, другой выбор. Выбрав версию портала,
поправь и его, иначе следующий читатель получит два противоречащих указания.

Библиотека объявляется внешней, чтобы webpack не клал её в бандл, а брал глобальную:

```js
// webpack.config.js
externals: {
  react: 'React',
  'react-dom': 'ReactDOM',
  echarts: 'echarts',
},
```

В коде тогда обычный импорт пакета — на сборке он превратится в обращение к `window.echarts`:

```ts
import * as echarts from 'echarts';
```

Условия, при которых этот путь работает: плагин не пользуется ничем, чего нет в версии портала,
и не вызывает `echarts.use(...)` — глобальная сборка уже полная. Проверять доступность перед
использованием обязательно: `window.echarts` может не оказаться, если портал сменит состав
скриптов.

### Ставим свою версию

Тогда обязательна **изоляция от глобальной**, иначе на странице окажутся два экземпляра
библиотеки, и часть состояния (реестр инстансов, зарегистрированные темы, расширения) у них
будет разной — симптомы получаются странные и плохо воспроизводимые.

Изоляция держится на двух правилах:

1. **Модульный импорт**, а не пакет целиком. Модульная сборка `echarts/core` не пишет себя
   в `window`, поэтому не конфликтует с глобальной:

   ```ts
   import * as echarts from 'echarts/core';
   import { BarChart } from 'echarts/charts';
   import { GridComponent, TooltipComponent, LegendComponent } from 'echarts/components';
   import { CanvasRenderer } from 'echarts/renderers';

   echarts.use([BarChart, GridComponent, TooltipComponent, LegendComponent, CanvasRenderer]);
   ```

   `import * as echarts from 'echarts'` тянет всю библиотеку — все типы диаграмм, оба
   рендерера — и в этом варианте не нужен.

2. **`echarts` не объявляется внешней.** Запись в `externals` заставит сборку взять глобальную,
   и своя версия просто не попадёт в бандл.

Смешивать пути нельзя: часть кода на глобальной библиотеке, часть на своей — это два
экземпляра, инстанс, созданный одним, не виден другому.

По умолчанию — своя версия. Дороже по весу, но снимает единственный по-настоящему неприятный
класс отказов: диаграмма перестала рисоваться после обновления портала, хотя плагин не менялся.

## Реализация адаптера

Файл — `src/modules/CustomChart/engine/engine.ts`, интерфейс рядом, в `engine/engine.types.ts`
(раскладка — скилл `custom-chart-module`). Имя `echarts` за пределами этой папки не
упоминается: спеку строит `model/buildSpec.ts`, ничего не зная о движке.

Тип спеки объявляется **в `engine.types.ts`**, а не здесь: его импортирует `buildSpec` из `model/`, и тянуть ради типа файл, который на верхнем уровне выполняет `echarts.use([...])`, незачем.

```ts
// engine/engine.types.ts
import type { EChartsType } from 'echarts/core';

import type { ChartSize } from '../hooks/useChartSize';

export type ChartSpec = Parameters<EChartsType['setOption']>[0];

export interface ChartEngine<TSpec, TInstance> {
  create: (element: HTMLElement) => TInstance;
  render: (instance: TInstance, spec: TSpec) => void;
  resize: (instance: TInstance, size: ChartSize) => void;
  destroy: (instance: TInstance) => void;
}
```

`ChartSize` **переиспользуется** из `hooks/useChartSize.ts` — он там уже объявлен и реэкспортирован из `index.ts` модуля. Второй одноимённый тип рядом даст два структурно одинаковых типа с разным местом объявления.

```ts
// engine/engine.ts
import * as echarts from 'echarts/core';
import type { EChartsType } from 'echarts/core';

import type { ChartEngine, ChartSpec } from './engine.types';

export const echartsEngine: ChartEngine<ChartSpec, EChartsType> = {
  create: (element) => echarts.init(element, null, { renderer: 'canvas' }),

  // Слияние, а не замена: см. раздел про setOption ниже.
  render: (instance, spec) => instance.setOption(spec, { notMerge: false, lazyUpdate: true }),

  resize: (instance) => instance.resize(),

  destroy: (instance) => instance.dispose(),
};
```

Объект — константа модуля, а не литерал в теле компонента: `chart-lifecycle` держит его в
зависимостях эффекта, и новый объект на каждом рендере пересоздавал бы инстанс.

**`echarts.init` на узле нулевого размера** пишет в консоль «Can't get dom width or height» и рисует пустоту. На первом кадре `useChartSize` отдаёт ровно `0×0`, поэтому создание инстанса ставится под условие ненулевого размера — см. `chart-lifecycle`, раздел про хуки.

## setOption: что сбрасывается

Самая частая ошибка — обновлять диаграмму через `notMerge: true`, потому что «так надёжнее».
Надёжнее не будет: сбросится всё состояние, которое пользователь навёл руками, — выключенные
в легенде серии, положение `dataZoom`, выделение.

| Режим                         | Когда                                                                 |
| ----------------------------- | --------------------------------------------------------------------- |
| `notMerge: false` (умолчание) | обычное обновление: данные пересчитались, структура прежняя           |
| `notMerge: true`              | сменилась структура: другой тип диаграммы, другой набор осей          |
| `replaceMerge: ['series']`    | число серий изменилось — старые нужно убрать, не трогая остального    |
| `lazyUpdate: true`            | несколько `setOption` подряд: перерисовка один раз, на следующий кадр |

Про `replaceMerge` стоит помнить отдельно: при обычном слиянии серии, которых больше нет в
новой спеке, остаются на диаграмме — данных для них нет, а легенда есть.

## События

`instance.on(event, handler)` **добавляет** обработчик, а не заменяет. Подписка внутри
обновления спеки — гарантированная ошибка: после десяти обновлений один клик вызовет
обработчик десять раз. Подписываться один раз на инстанс, снимать в `cleanup`:

```ts
useEffect(() => {
  const instance = instanceRef.current;
  if (!instance) return undefined;

  instance.on('click', handleClick);
  instance.on('mouseover', handleHover);
  instance.on('mouseout', handleOut);

  return () => {
    instance.off('click', handleClick);
    instance.off('mouseover', handleHover);
    instance.off('mouseout', handleOut);
  };
}, [instanceRef, handleClick, handleHover, handleOut]);
```

Обработчики должны быть стабильными (`useCallback`), иначе эффект переподписывается на каждом
рендере. `instance.off('click')` без второго аргумента снимает **все** обработчики события —
годится, когда плагин единственный владелец инстанса.

## Точка данных тащит исходную строку

Событие ECharts не знает ничего о полках и датасетах: в `params` приходят `seriesIndex`,
`dataIndex`, `name`, `value` — то есть индексы, а не поля конфига. Чтобы обработчик клика мог
собрать категорию, значение и поле для `drillDown`, исходная строка кладётся **в саму точку**
при построении спеки:

```ts
// `valueField.id` — id пилюли полки «Значения» из конфига: под ним `remapData` кладёт число.
{ value: row[valueField.id], name: row.categories, dataContext: row }
```

Так сделано в референсном генераторе спеки, и это правильный приём: `params.data.dataContext`
даёт обработчику всю строку без обратного поиска по индексам. Обратный путь — искать строку
по `dataIndex` в исходном массиве — ломается при любой сортировке или фильтрации внутри спеки.

Дальше строка превращается в доменное событие чистой функцией (`toChartPoint` из
`chart-lifecycle`), и только потом уходит в инжекты ядра.

## Рендерер

**Умолчание проекта — `canvas`**, как у штатных диаграмм ядра: плагин ведёт себя так же, как соседние компоненты отчёта, и не упирается в число точек.

`svg` — осознанная замена, а не альтернатива по вкусу. Менять стоит, когда у плагина много текста и его печатают или выгружают в PDF: там `canvas` мылит. Заодно `svg` даёт узлы в DOM, то есть проверяемую тестами разметку, — но ради тестов рендерер не меняют, спека проверяется чистой функцией.

| Рендерер                | Когда                                                     |
| ----------------------- | --------------------------------------------------------- |
| `canvas` (по умолчанию) | тысячи точек, частая перерисовка, анимация                |
| `svg`                   | много текста, экспорт в PDF, печать отчёта, немного точек |

Менять рендерер у существующего инстанса нельзя — только пересоздав его, то есть через
`destroy` и `create`.

## Один узел — один инстанс

`echarts.init` на узле, где инстанс уже живёт, выдаёт предупреждение в консоль и создаёт второй
экземпляр поверх первого. Практический симптом — диаграмма, которая рисуется дважды и «мигает»
при наведении.

Причина почти всегда одна: инстанс не уничтожен там, где узел переиспользуется. Проверка перед
созданием стоит дёшево:

```ts
const existing = echarts.getInstanceByDom(element);
if (existing) existing.dispose();
```

Но это лечение симптома. Правильный порядок — `destroy` в `cleanup` эффекта, как в
`chart-lifecycle`; проверка нужна лишь там, где узлом владеет ещё кто-то.

`dispose()` обязателен: инстанс держит DOM-узлы, слушателей и таймеры анимаций. В референсной
ветке его нет ни одного — переоткрытие отчёта копит инстансы.

## Спека строится под свои данные

Готовые генераторы спеки из чужих плагинов выглядят соблазнительно, но переносят вместе с
формой серий и свою схему ключей. Типичный пример — плагин, который переименовал трейсы в
`values0`, `values1`, `fieldName0` и строит спеку по этим именам. Это его внутреннее решение,
а не правило ядра: как называются ключи в строках, решает `remapData` **твоего** адаптора
(см. `data-query-contract`). Спека читает то, что положил адаптор, — и ничего другого.

Что действительно стоит повторять — три структурных приёма, независимых от плагина:

- точка данных несёт исходную строку (`dataContext`) — см. раздел выше;
- ветка «есть серии / нет серий»: с полкой «Серии» точка превращается в набор дочерних
  значений, без неё остаётся плоской;
- цвет точки приходит из строки (`itemStyle.color`), если плагин поддерживает раскраску по
  полю, и остаётся `undefined`, когда поля нет, — тогда действует палитра из спеки.

## Тестирование

Спека — чистая функция, и это основная масса тестов: `buildSpec(config, plotData, theme)`
проверяется в окружении `node`, без DOM и без библиотеки.

Сам движок в тестах не запускается. Модуль `echartsEngine` подменяется фиктивным объектом с
теми же четырьмя функциями — проверяется порядок вызовов, а не картинка. Если понадобится
замокать саму библиотеку (например, в спеке на подписки), мок кладётся на `echarts/core`:

```ts
jest.mock('echarts/core', () => ({
  use: jest.fn(),
  init: jest.fn(() => ({ setOption: jest.fn(), resize: jest.fn(), dispose: jest.fn(), on: jest.fn(), off: jest.fn() })),
  getInstanceByDom: jest.fn(),
}));
```

**Плата за модульный импорт видна именно в тестах.** Подпути `echarts/*` и `zrender/lib/*`
объявлены в `exports` пакета без `require`-условия, поэтому спек, дотягивающийся до реального
модуля, падает на `Unexpected token 'export'`. Лечится не правкой кода, а строкой в
`transformIgnorePatterns` (`jest.config.js`) — исключением этих путей из общего «не
трансформировать `node_modules`». Симптом типовой: правишь реализацию по кругу, а ошибка
остаётся той же — это про окружение, а не про код (CLAUDE.md, «Когда правки зацикливаются»).

**Смоук-тест поверх настоящей библиотеки стоит одного файла.** Собранная спека прогоняется
через реальную ECharts и ловит то, чего не видит проверка объекта: незарегистрированный
компонент, недопустимое значение опции, падение внутри `renderItem`. Рендерер в нём — **`SVGRenderer`,
зарегистрированный локально в самом спеке**: `CanvasRenderer` в node без `canvas` не работает,
а `echarts.use` идемпотентен, так что регистрация в спеке не пачкает бандл плагина.

Легенда — частный случай той же ошибки: если спека всегда кладёт `option.legend`, компонент
`LegendComponent` обязан быть зарегистрирован даже при выключенной легенде, иначе ECharts
пишет предупреждение в консоль на скрытую легенду.

## Проверка в портале

То, чего не покажут тесты: диаграмма появилась вообще; выключенная в легенде серия осталась
выключенной после обновления данных (значит `notMerge` не сброшен); клик по точке дал
правильную категорию (значит `dataContext` доехал); перетаскивание границы плитки
перерисовало диаграмму без обрезки; после переоткрытия отчёта в DevTools нет второго
`<canvas>`/`<svg>` внутри контейнера.
