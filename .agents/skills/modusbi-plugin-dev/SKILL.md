# Разработка плагинов визуализации ModusBI

Помогай создавать, изменять, проверять и собирать визуализации ModusBI в репозитории
пользователя. Один скилл содержит тематические справочники; загружай только нужные.
Инструкции пользователя и правила его проекта имеют приоритет над рекомендациями скилла.

## Начало работы

1. Найди **корень целевого плагина**, прочитай действующие `AGENTS.md`, `package.json`,
   конфигурацию сборки и затронутые файлы. Все пути `src/`, `prebuild/`, `docs/`, `build/`
   ниже относятся к этому корню, а пути `references/`, `scripts/`, `assets/` — к каталогу
   **этого скилла**. Не считай текущий каталог или место установки скилла корнем плагина.
2. Определи задачу: новый плагин, изменение поведения, диагностика, ревью, синхронизация
   контракта, миграция, портальный UC или упаковка. Для нового плагина выясни вид диаграммы,
   полки и ожидаемый результат; используй custom-chart как каркас. У шаблона есть заглушки,
   зелёная сборка сама по себе не означает готовую визуализацию.
3. Проверь состояние рабочего дерева, доступные npm scripts и версию ядра. Версии из
   [карты проекта](references/project-context.md) — снимок исходника, не требование обновлять
   существующий плагин. Не меняй зависимости, движок и раскладку чужого проекта заодно.
4. Если ответ не следует явно из задачи, кода, контракта или согласованных решений —
   уточни его у пользователя. Собери связанные вопросы вместе; продолжай независимую часть.
   Не подменяй отсутствующий контракт, ответ сервера или продуктовое решение догадкой.

Для изменения поведения зафиксируй: вход, наблюдаемый результат, пустые/непригодные данные,
ошибка запроса, конфиг старого отчёта. Используй уже определённое поведение; для неприменимых
пунктов кратко укажи причину. Недостающие решения уточняй до зависимой реализации.
Не требуй эти пять пунктов для простой правки документации или чистого ревью.

## Постоянные ограничения

- Контракт целевого ядра: `prebuild/api/chartPlugin.d.ts` и `version.json`; локальный снимок:
  `src/types/chartPlugin.d.ts`. Без ядра можно проверять внутреннюю согласованность по снимку,
  но нельзя заявлять актуальность относительно портала или выполнять синхронизацию вслепую.
- `prebuild/` — поставка ядра, не место исправления плагина. Читай её для диагностики;
  изменения кода делай в исходниках плагина. Не исправляй типы ядра под реализацию.
- Сохрани семь runtime-экспортов: `CustomChart`, `CustomReducers`, `CustomSettings`,
  `CustomAxes`, `DataAdaptor`, `SpecGenerator`, `ConfigEditor`, а также `ContractCheck`.
- `react` и `react-dom` предоставляет ядро; JSX — classic. UI ядра поступает через
  `pluginImports`. Библиотека отрисовки выбирается задачей, ECharts не подразумевается всегда.
- Контрактная сигнатура важнее общих правил числа аргументов или стиля. `unknown` с проверкой
  формы — граница неизвестных данных; `any` в дословном снимке ядра не переписывай.
- Дефолты, отсутствие поля, `null`, `false` и `0` различаются. Не подменяй их без решения о
  поведении. Для настроек проверь весь путь UI → команда → configDraft → autoApplySettings.
- Хуки Claude и их permissions здесь **не устанавливаются**. Ограничения путей и проверки
  выполняет агент явно; это не автоматическая блокировка инструментов и не файловая песочница.
  После законченной TS-правки выполняй typecheck; промежуточный RED/перенос деклараций может
  быть красным, итоговая реализация — нет.
- Сабагенты необязательны. Один агент выполняет этапы последовательно. При отдельно
  разрешённой делегации можно разделить роли из TDD; наличие скилла само её не разрешает.

## Проверка и сдача

В целевом проекте выполни доступные проверки, требуемые изменением: связанные спеки, затем
`npm test -- --runInBand`, `npm run typecheck`, `npm run lint`; сборку — при изменении сборки,
runtime-кода или упаковке. Для изменения кода отформатируй изменённые файлы проектным Prettier.
Сначала прочитай scripts: команды шаблона могут отличаться в другом плагине. Скрипт `test`
исходника допускает отсутствие тестов — проверь, что нужные спеки реально выполнялись.

После изменений контракта выполни ревью из `sync-contract`; после изменений панели,
редьюсера или дефолтов — ревью цепочки из `new-setting`. При запросе только на ревью
сначала выдай находки с файлами, последствиями и предложенными исправлениями, не меняя код.

Три неудачных исправления одной причины — повод сменить гипотезу: сохрани текущий diff,
сверь контракт/данные/окружение, сузь воспроизведение. Не делай `git reset`, `checkout --`
или общий stash поверх пользовательских правок. Отмени только собственные известные изменения
точечным патчем, если это нужно. Недостающий факт или решение уточни у пользователя.

В ответе укажи результат, изменённые файлы, реально выполненные проверки и ограничения.
Отдельно различай локальную корректность, проверку архива и подтверждение на портале.
Не выдавай непроверенный сценарий за успешный и не останавливай всю задачу из-за отсутствия
необязательного инструмента. История переноса и границы доказательств —
[источники](references/sources.md); открывай их при сверке версии или обновлении скилла.
