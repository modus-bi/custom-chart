# Запрос, кэш и преобразование данных

Описанные runtime-детали — знания исходного комплекта о ядре 3.16.3. `chartPlugin.d.ts`
не раскрывает форму config/spec/data. При расхождении сверяй целевой бандл и фактический
обезличенный ответ; отсутствие доступа не заменяй уверенной выдумкой.

## Диагностика по цепочке

`ConfigEditor → config.axes[].fields → datasetId → getQueryObjects → loadDatas →
data/datas[cacheId] → refresh → aggregateBypass → remapData → plotData → buildSpec`.

Начинай с первого отсутствующего звена. В шаблоне ConfigEditor не сохраняет поля, sortAxes
возвращает пустую панель, getQueryObjects — [], а методы преобразования — заглушки.
Исправление только remapData не заставит такую цепочку отправить запрос.

## Запрос

`getQueryObjects(config, exportMode = null, settings = {})` сохраняет контрактную сигнатуру.
Результат — массив описаний трейсов, не один запрос на все значения. Применяй актуальную
ёмкость selectedFieldIndex и hideResult **до** формирования трейсов; `details` в описанном ядре
тоже идёт как отдельный трейс значения. Число трейсов оценивай по активным участвующим полям,
не по любому числу пилюль на экране.

Сначала собери группирующие series/categories, затем значения. Общие group/order/distinct/limit
должны совпадать у трейсов: mergeTraces читает их из первого. Дедупликация group — по name.

| Секция | Содержание |
| --- | --- |
| select | Сначала поле значения, затем группирующие поля |
| group | Поля группировки без дубликатов name |
| order | Сортировка по field.order/orderIndex |
| where | Описание фильтров where и без filterSqlType |
| having | Вычисляемые фильтры с filterSqlType='having' |
| options | seriesAutoFill из config.series.autoFill |
| variables | config.variables, если заданы |
| limit | config.rowsLimit |

Значения фильтров идут отдельным третьим аргументом loadDatas (`config.filters`). mergeTraces
восстанавливает where/having из этих значений; описание having помогает найти name/calc.
Не рассчитывай, что собственная where-секция будет отправлена серверу буквально.

В select нужны проверенные поля: name (или `[name, ...parameters]`), aggr из agg, alias,
id пилюли, локализованный fieldAlias, lvl с дефолтом 0, valueType. Для countd — count и
distinct:1. Вычисляемое calc декодирует `!hs_quote!` в апостроф. Сортировка/подпись/цвет по
другому полю добавляют `_sortBy`/`_labelBy`/`_colorBy` с соответствующей агрегацией.
subMode, экспортные режимы и переменные добавляй по требованию, с проверкой целевого ядра.

Исходный учебный getQueryObjects не реализует ёмкость, hideResult, HAVING, countd и часть
прочих правил — здесь он намеренно не предлагается как готовая реализация. Для пустых полок
не смешивай внутреннее `false` CommonDataAdaptor с `[]` типизированного метода плагина:
сохраняй сигнатуру своего контракта и не отправляй бессодержательный запрос.

## Алиасы и ответ

| Данные | Ключ |
| --- | --- |
| Значение в запросе | `[values]`; индекс трейса добавляет mergeTraces |
| Детали | Также `[values]`, алиаса `[details]` нет |
| Одна категория / серия | `[categories]` / `[series]` |
| Несколько категорий | `[categories][i]` при ёмкости -2 |
| Несколько серий таблицы | Суффикс по правилам chartType='table' ядра |

Бэкенд возвращает таблицу; **ядро само** вызывает splitTraces до записи в store:

1. `[values][n]` становится отдельным трейсом с ключом `values`.
2. Точные `[categories]`, `[series]`, `[identity]`, `[linkage]`, `[node]` теряют скобки.
3. Остальные ключи, например `[categories][0]` и `[categories][0]_sortBy`, сохраняют скобки.
4. Измерения копируются в каждый трейс. При отсутствии values есть иная ветка преобразования;
   groupByOptimization также меняет состав измерений. Не применяй правила обычных трейсов
   к этим ответам без наблюдения.

Не вызывай splitTraces повторно в плагине. Отделяй HTTP-ответ до splitTraces от props после
него; отмечай этот уровень в метаданных фикстуры.

## cacheId и автообновление

Ядро может считать props.cacheId по своему CommonDataAdaptor, а loadDatas — по запросу плагина.
При разных запросах ответ попадает в другую ячейку. Принятое решение исходника:

```ts
loadDatas(datasetId, null, config.filters, queryObjects, { editor, componentId }, cacheId);
const response = data ?? (cacheId ? datas?.[cacheId] : undefined);
```

Расширь локальный тип LoadDatas до шестого аргумента и props до datas. Это пример механики,
не готовые объявления типов. Обрабатывай fetching, error/errorMsg/msg, cached и cropped;
не строй адаптер при ошибке или ещё не полученном ответе.

Настройка, известная только плагину, может менять запрос без смены cacheId: для перезапроса
используй reloadDatas с теми же шестью аргументами. loadDatas может вернуть существующий кэш.
Явно отслеживай значимые входы запроса, чтобы не сохранить прежнюю выборку после их изменения.

DataOptionsContent пишет refresh/refreshTime, но таймер данных создаёт плагин. Интервал —
refreshTime * 1000, callback вызывает reloadDatas; учитывай только положительный конечный
интервал. Последние инжекты/данные храни в ref, зависимости таймера — устойчивые примитивы,
в cleanup — clearInterval. Не перезапускай таймер на каждый новый объект config/callback.
Автообновление данных отличается от авто-применения настроек. Работу таймера в редакторе
согласуй, если правило отсутствует. Новые поля старых отчётов читай через readConfigField.

## Уровни адаптера

- source — исходные данные, с учётом формы datasetId и лимитов проекта.
- aggregated — трейсы; строка содержит values и метаданные своей пилюли
  (id/name/fieldName/fieldAlias/fieldTitle/traceKey).
- plotData — формат конкретной визуализации. Значения адресуются **id пилюли**, не display name
  или строкой «имя (агрегация)»: одинаковые поля иначе перезапишут друг друга.

Если сводишь трейсы по индексу, сначала подтверди выравнивание строк и длины. Иначе нужна
доказанная связь по ключам измерений, а не молчаливое соединение чужих строк. Измерения можно
переносить в plotData или читать из aggregated; ядровой remapData не гарантирует их перенос.
Не смешивай служебные метаданные и значения; не превращай null в 0 без требования.

## Проверка

getQueryObjects: активные/скрытые поля, ёмкости, две одинаковые пилюли, группировки в каждом
трейсе, алиасы, filters/HAVING, countd, сортировка и пустота. Для remapData нужна обезличенная
фикстура **из целевого портала** с двумя значениями и двумя категориями, если такой сценарий
поддерживается плагином. Зафиксируй версию ядра, config и уровень ответа.

Без фикстуры можно написать явно синтетические unit-тесты преобразования, но подтверждение
контракта ответа остаётся «не проверено». Если задача требует реализации по неизвестному
ответу, уточни источник у пользователя и продолжай независимые части. Удаляй временное
логирование, не сохраняй полные пользовательские выборки.
