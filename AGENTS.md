# Инструкции для работы с custom-chart

## Язык и назначение проекта

Отвечай пользователю по-русски. Тексты интерфейса и полезные комментарии также пиши по-русски.

Это шаблон плагина визуализации **ModusBI**, а не самостоятельное React-приложение.
Webpack собирает единый UMD-бандл `build/custom_chart_0.js` с именем `CustomChart0`.
React и ReactDOM предоставляет ядро портала. Библиотеку отрисовки выбирает задача:
наличие справочника по ECharts не означает, что его нужно устанавливать.

В исходном шаблоне есть намеренные заглушки: преобразование данных, сохранение полей,
порядок полок, панель настроек, редьюсер и отрисовка. Успешная сборка не доказывает,
что визуализация работает. При ревью отличай заготовки шаблона от регрессий готового плагина.

## Навык Codex

Для разработки, диагностики, ревью, миграции и упаковки плагина используй
[modusbi-plugin-dev](.agents/skills/modusbi-plugin-dev/SKILL.md).
Прочитай его `SKILL.md`, затем только справочники, относящиеся к задаче;
таблица выбора находится внутри навыка. Не загружай все справочники заранее.

- При первом знакомстве с архитектурой прочитай карту проекта из навыка.
- Для TS/TSX используй правила TypeScript; для изменения поведения — процесс TDD.
- После изменения экспортов, `CustomAxes` или снимка типов выполни ревью контракта.
- После изменения настроек, редьюсера или дефолтов проверь всю цепочку применения настройки.
- Для проверки на портале используй вместе справочники `portal-integration-testing` и `uc-testing`.

`.claude/` и `CLAUDE.md` содержат конфигурацию и инструкции Claude Code.
Для Codex рабочие инструкции — этот файл и `.agents/skills/`.
Хуки, permissions и роли из `.claude/` автоматически не подключаются:
проверки запускай явно. Отдельные агенты не обязательны; последовательный TDD допустим.
Делегируй только при разрешённой в текущей среде и задаче делегации.

## Перед изменениями

1. Проверь `git status`, прочитай `package.json`, затронутые файлы и существующие тесты.
2. Бери факты из кода, контракта и наблюдаемых данных. Недостающие продуктовые решения
   уточняй одним списком вопросов, продолжая независимую работу. Ранее согласованное не спрашивай повторно.
3. Для изменения поведения зафиксируй вход, ожидаемый результат, пустые/непригодные данные,
   ошибку запроса и совместимость со старым конфигом. Неприменимые пункты отмечай с причиной.
   Для простой правки документации этот процесс не нужен.
4. Сохраняй пользовательские изменения. Не выполняй общий reset, checkout или stash,
   не меняй зависимости, архитектуру и соседний код вне объёма задачи.

Если три попытки исправления одной причины не дали результата, пересмотри гипотезу:
сверь контракт, данные и окружение, сузь воспроизведение. Откатывай только собственные
известные изменения точечными правками.

## Контракт с ядром

- Источник истины: `prebuild/api/chartPlugin.d.ts` и `prebuild/api/version.json`.
  Перед изменением контрактных экспортов прочитай актуальный контракт.
- [src/types/chartPlugin.d.ts](src/types/chartPlugin.d.ts) — локальный снимок для типизации.
  Синхронизируй его по поставке ядра с сохранением шапки происхождения и версий;
  не подгоняй декларации под удобную реализацию. `any` в дословном снимке не переписывай.
- `prebuild/` — распакованная поставка ядра, доступная для чтения и диагностики.
  Не исправляй в ней код плагина: папка игнорируется Git и заменяется при обновлении ядра.
- Если ядро недоступно, используй локальный снимок и явно укажи, что актуальность
  относительно целевого портала не проверена. Не выполняй синхронизацию без источника.
- [docs/api](docs/api) — исторический неформальный конспект. При расхождении верь `.d.ts`;
  неописанную форму данных сверяй с реализацией и обезличенным реальным ответом.
- Сохраняй семь runtime-экспортов: `CustomChart`, `CustomReducers`, `CustomSettings`,
  `CustomAxes`, `DataAdaptor`, `SpecGenerator`, `ConfigEditor`.
  Сохраняй также тип `ContractCheck`, проверяющий фактические экспорты через `typeof Self`.
  Он не запрещает дополнительные экспорты и не заменяет проверку поведения.

Проверка совпадения локального снимка с поставкой, из корня репозитория:

```bash
node .agents/skills/modusbi-plugin-dev/scripts/check-contract.mjs .
```

## Код и архитектура

- Код модулей, менеджера и точки входа — TypeScript strict. Используй `import type` для типов,
  `unknown` с проверкой формы для неизвестных данных и относительные импорты.
- JSX — classic, с импортом React. Общие опции SWC находятся в `swc.config.js`;
  webpack и Jest используют этот пресет. Не переключай JSX runtime заодно с задачей.
- `react` и `react-dom` должны оставаться внешними зависимостями. UI и готовые секции ядра
  получай через `pluginImports.components`, `pluginImports.sections`, `pluginImports.services`.
- Соблюдай раскладку `CustomChart`: `model/`, `ui/`, `hooks/`, `lib/`, `engine/` по назначению.
  Публичный вход модуля — `index.ts`; подробные правила и исключения — в справочнике навыка.
- Сохраняй цепочку своей настройки: UI → `changeChart` → команда → `configDraft` →
  `options.autoApplySettings(state)`. Готовые секции ядра могут менять черновик собственными
  колбэками. Учитывай ручное применение и старые отчёты без нового поля.
- Не смешивай отсутствие поля, `null`, `false` и `0`. Дефолтный конфиг возвращай независимой копией.
- Для данных используй `structuredClone`, для неглубоких правок — spread.
  Не клонируй через `structuredClone` функции, React/DOM-узлы или объекты, которым нужен прототип.
  Не добавляй `react-addons-update` и не используй `_.cloneDeep` в новом коде без необходимости.
- SCSS/CSS включаются в JS через `style-loader`; отдельный CSS-файл портал не подключает.
  Форматирование определяет проектный Prettier. Не форматируй весь репозиторий заодно.

## Команды и проверки

Используй версии Node и npm из `package.json` (`engines`). Зависимости устанавливай по lock-файлу.
Команды выполняй из корня проекта; используй локальные инструменты, не скачивай случайные версии через `npx`.

| Команда                                                   | Назначение                                                                 |
| --------------------------------------------------------- | -------------------------------------------------------------------------- |
| `npm ci`                                                  | Установка зависимостей из lock-файла                                       |
| `npm start`                                               | Портал с локальным плагином и HMR; нужны ядро и конфигурация в `prebuild/` |
| `npm test -- --runInBand --runTestsByPath <путь-к-спеку>` | Связанный тест                                                             |
| `npm test -- --runInBand`                                 | Полный набор Jest                                                          |
| `npm run typecheck`                                       | TypeScript без генерации файлов                                            |
| `npm run lint`                                            | ESLint                                                                     |
| `npm run build`                                           | Production-бандл                                                           |
| `npm run build:dev`                                       | Диагностический бандл                                                      |
| `npm run build:plugin`                                    | Архив ModusBI при наличии сборки и `build/manifest.json`                   |

Для изменения поведения используй RED → GREEN → REFACTOR. Спеки `*.spec.{js,jsx,ts,tsx}`
лежат рядом с кодом; компонентные тесты включают `/** @jest-environment jsdom */`.
Моки `pluginImports` должны сохранять реальный API ядра.

После изменения кода выполни связанные тесты, полный Jest, typecheck и lint.
После изменения runtime-кода, сборки или при упаковке выполни также production-сборку.
Скрипт `test` допускает отсутствие тестов: проверь, что нужные спеки действительно запускались.
После законченной TS-правки запускай typecheck явно; промежуточный RED может быть красным,
итоговая реализация — нет. Для правок только документации достаточно проверки текста,
ссылок и форматирования; запуск сборки и тестов не требуется.

## Портал, упаковка и сдача

Dev-сервер использует порт 7000 по умолчанию или `PORT`; плагин доступен как
`/plugins/custom_chart_0.js`. Для его проверки отчёт должен содержать `CustomChart0`.
Локальные `prebuild/`, доступ к сети и авторизация не переносятся в облачную среду автоматически.
Учётные данные вводит пользователь; не проси пароль или токен в переписке.

Упаковку выполняй по справочнику `package-plugin`: архив `<manifest.name>.tar.gz` должен
содержать только `plugin.js` и `manifest.json` в корне. Независимо проверь его помощником
`verify-package.mjs` из навыка. Успешный exit code сборщика сам по себе не доказывает наличие
корректного архива. Не меняй версию, не коммить сборку и не публикуй плагин автоматически.
Установка на портал и изменения отчётов выполняются в разрешённом пользователем объёме.

В итоговом ответе укажи результат, затронутые файлы, фактически выполненные проверки
и ограничения. Различай локальные тесты, проверку архива и проверку на портале:
одна не доказывает другую. При запросе только на ревью сообщи находки и последствия без правок кода.
